**I. What (a)–(d) are, set-theoretically — and the unification that falls out**

The bowl is a set of identified records, each an ordered tree. Against that set, the four roles are not four file formats — they are the four classical relationships a collection of statements can have to a set:

- **(a) and (b) are *extension*** — the partition that physically holds the set. (a) is the singleton cell (one record per cell, filename as key); (b) is the multi-cell (many records per cell, internal order). Every record lives in exactly one cell: that's what makes them *storage*, and it's why their problems are storage problems (the lost update, RMW discipline, partition-as-isolation).
- **(c) is *composition*** — the admission that records and cells aren't coterminous: a record assembled as the union of fragments across files, with the assembly declared (the host supplies the element line; the include supplies the interior; pre/postfilters are the morphisms). Set-theoretically it's the statement that membership in the bowl and residence in a cell are different relations.
- **(d) is *intension*** — a subset defined by predicate rather than enumeration, plus two things pure set theory doesn't give you: edge-data on the membership relation (the view's own content — the RDF-star lesson) and an order on the selection.

And here is the unification that today's algebra spike quietly completed, which I think is the single most consequential sentence available tonight: **schemas, views, queries, and censuses are one object — intensionally defined subsets of the bowl, closed under union, intersection, and difference.** A schema is τ plus fiat seats. A generated view is τ plus a projection function. A census is |τ_old \ τ_new|. A path's selection half is τ with arity bounds. SQL's deep lesson was never tables — it was that a *closed algebra of selections* is what makes a store feel alive, because every question composes with every other question. We now have that algebra, it's decidable on the shorthand fragment, and it arrived from the schema side without being asked to be a query language. That's why the "brilliantly responsive sql-like disposition" is not a separate invention: SELECT is type membership, WHERE is the row constraints, JOIN is reference resolution (the resolver — agents already address relationally), GROUP BY is partition by name/trait, ORDER BY is document order or the view's declared order. The query language is the schema language is the census language. One algebra, four costumes.

CRUD then decomposes honestly rather than transplanting:

- **Create** = admission through the membrane, with expectation bounds (O15) — a command, in the CQRS sense.
- **Read** = intension → extension resolution, at whatever grain (record, part, selection).
- **Update** *does not exist at the semantic layer* — it decomposes into append + supersede, which is exactly what stacking already means. UDON refused last-wins at the parse layer years before this conversation; the store inherits the same metaphysics one altitude up.
- **Delete** decomposes into tombstone + censused contraction + **sink** (your throw-away sinks, now structural: material superseded before integration terminates in the discard channel, and the census is honest only because the sink term exists).

Notice what happened: the language's own keep-everything/severity-is-loss commitments, made for parse-layer reasons, turn out to be **event-sourcing's core axiom arrived at independently** — nothing is destroyed; the current state is a *fold*; all mutation lives in the interpretation, not the substance. The language and the store share one metaphysics. That is why this database wants to exist on top of this format and not on top of YAML: the format already believes what the store needs to believe.

**II. The temporal axis — skipping to the lede**

The proven concepts we should inherit whole rather than reinvent over five years, named with their exact points of contact:

**Event sourcing / CQRS.** State = fold(event log). Write side: commands through the membrane (that's Create above — validation, expectation bounds, two-outcome refusal). Read side: projections, regenerable — which is precisely the (d)-generated role. CQRS isn't an architecture we'd be adopting; it's the architecture the roles already describe, with the membrane as the command validator and (d)-generated as the read models.

**The datom shape (Datomic), which is the existence proof for your whole ask.** Datomic demonstrated, in production, for fifteen years, that "a current-state store with a real temporal axis and a responsive declarative query language" is achievable and beloved — and its primitive is (Entity, Attribute, Value, Transaction, assert/retract). The mapping onto UDON is almost embarrassing: `element[key]` is E; the stacked attribute is A with *accumulate-never-overwrite* — **UDON's stacking is Datomic's accumulation semantics, arrived at from the honesty side rather than the temporal side**; and the transaction... we already have. **Git commits are the transaction grain.** The letter called git "an unused second grain of atomicity"; the sharper statement is that git is the *transaction log we never have to build* — `git show <ref>:<path>` is as-of, already shipped, corpus-consistent by construction. as-of / since / history queries — Datomic's three temporal verbs — all become folds over commit ranges. No WAL to invent, no second store to keep fresh (which the staleness constraint from thought #1 forbids anyway): git stays the only primary; everything else is projection.

**Where the events come from — and the fiat-strata symmetry that decides it.** Two sources, both needed, and the split is principled rather than convenient: the *mechanical* skeleton of the event stream is **derivable** — a schema-aware diff of folds between commits, which the algebra makes computable at record grain (which records entered/left which τ; which stacks lengthened; which keys moved). But the *intent* — why, decided by whom, superseding what — is **not derivable from any diff, ever**. That's P3 (reasons exist only if captured) arriving on the time axis, and it's why O16's breadcrumb-routing isn't a courtesy feature: explicit events written at the change site are the *testimony half* of the event stream, and the derived diff is its *skeleton half*. Event = derived-delta ⊕ attached testimony. The strata's description/decision split, running temporally.

**Incremental view maintenance** (differential dataflow lineage) is the proven math for "brilliantly responsive": projections that update from the event delta rather than recomputing — with the honest note that for this estate's scale, recompute-on-read is fine for years, and IVM is the known escape hatch when it isn't, not a day-one need.

**And one place we genuinely extend rather than inherit** — worth flagging because it may be the estate's contribution back: the field's temporal state of the art is *bi*temporal (transaction time + valid time, XTDB). This estate's records already carry at least **four** times: committed-at (git), asserted-at (the record's own dates), valid-from (when the decision took effect), and — the tribunal's addition — *expires-or-revisits-when*, the pre-registered future time. Prospective validity is the column the rationale-structure sweep found empty in forty years of literature, and here it shows up as a *temporal coordinate*. Multi-temporal document stores with pre-registered expiry: as far as I can see from here, that quadrant is ours to occupy.

**III. Starter layouts — the shapes as fold-interpretations**

A starter layout, in this frame, is a *named binding* of: role assignments + event grain + default projections + membrane defaults. The estate already runs five, unnamed:

1. **Registry** — directory of (a)-files, filename = key (relata, terminology). Cleanest case: file diff *is* record diff, events fall out of git for free, directory = type extension.
2. **Ledger** — one (b)-file, append-heavy, homogeneous type (vivarium's DECISIONS). Needs the RMW/single-writer discipline; wants the current-truth projection; *is* the tribunal's waiting customer.
3. **Dossier** — one record spanning regions/sidecars (the cluster record; body + Working Notes + changelog). Per-part clocks, publication postfilters; (c)-composition inside one logical record.
4. **Corpus-and-spine** — (a)-population + (d)-authored view (ASF segments + OUTLINE). The authored view's edge-data is first-class content; ordering constraints checked against the dependency DAG.
5. **Spool** — membrane staging directory (relata ingest). Pure command-side; the two-outcome refusal lives here.

The reason starter layouts matter more than they look: they're the **O9 friction-killer**. "The right way" stops being a study of governance theory and becomes *picking a name* — you say "this is a ledger," and the verbs, the membrane defaults, the projections, and the event grain arrive as a bundle, each individually overridable. Rails' scaffolds, but for corpus governance — and every one of the five is already validated by years of shipped practice here; we'd be naming, not designing.
