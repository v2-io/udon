# GFM Dominates Usage, yet Frontier Models Write Every Dialect

GitHub Flavored Markdown on a CommonMark core is the de facto Markdown by every usage measure available in October 2026. It is the default in the most-downloaded parsers on every registry, there are roughly **250–273M `.md` files on GitHub** against 5.5M `.mdx` files and about 10k Djot files, and its relative share is rising faster than any rival's once npm's roughly 3× download inflation in 2026 is subtracted (inside the remark ecosystem, the GFM plugin went from 11% to 77% of parses between 2022 and 2026). The other dialects are each tied to one toolchain and one population. MDX holds the React docs world but is losing relative share. The Pandoc family (pandoc, R Markdown, Quarto) holds academic and data publishing and is consolidating under Quarto. Obsidian has the largest authoring base outside GFM and is still growing. MyST serves scientific Python, and Markdoc is small. Djot, John MacFarlane's redesign that fixes what he regrets in CommonMark, is three to five orders of magnitude smaller than the mainstream and shows no adoption inflection four years after launch. On LLM familiarity, the result runs against that ordering. Told which dialect to write, the strongest models tested (Claude Opus 5.5, Sonnet 5.5, Fable 5.1) produced parser-clean documents in all eleven dialects tried, Djot included. Weaker or older models (Haiku 5.5, Grok 4.7, Gemini 3.8 Flash, Sonnet 4.6, gpt-oss-120b) carried GFM and Pandoc habits into the less common dialects. So uptake predicts which dialect a weaker model fails first, but not what a frontier model can do. It does predict defaults: with no dialect named, every model emits the same unnamed hybrid (GFM tables and footnotes, GitHub alert syntax, `$` or `\(` math, `==` or `<mark>` highlights). No single spec defines that hybrid, and it never takes the Djot, Pandoc or MDX reading of an ambiguous glyph. Three limits apply throughout. The probes are single samples. No GPT-5.x or Gemini Pro model could be reached. Every usage number is a proxy for authorship, not a count of it.

## Only CommonMark has a rigorous spec, and it has not moved since January 2024

The six dialects Joseph named, plus the other sizable players, differ less in features than in *what kind of thing* each one is. The table below is the map. The sections after it give the evidence.

**CommonMark** is the one dialect with a precise, example-driven, versioned specification, and it has stopped moving. The current version is **0.31.2, dated 2024-01-28**, with 652 embedded examples that double as conformance tests ([CommonMark spec index](https://spec.commonmark.org/); [CommonMark 0.31.2](https://spec.commonmark.org/0.31.2/)). A 1.0 was promised for 2016, then 2017, and has never shipped. A 2025 forum post making "the case for calling it Version 1.0" drew no reply from MacFarlane ([talk.commonmark.org #4957](https://talk.commonmark.org/t/the-case-for-calling-it-version-1-0/4957)). His own verdict on the spec he edits is unusually blunt: he writes of "the 17 discouragingly complex rules" for emphasis, reference links whose status "can't [be told] … until we've parsed the entire document," and an "ugly heuristic" for lists interrupting paragraphs, and confesses, "I despair, at times, of getting to a spec that is worth calling 1.0" ([Beyond Markdown](https://johnmacfarlane.net/beyond-markdown.html)). The reference implementations remain active, and commits since 0.31.2 are clarifications such as a rewritten suggested emphasis algorithm and a BOM note ([commonmark-spec commits](https://github.com/commonmark/commonmark-spec/commits/master)). CommonMark is best read as a fixed, trustworthy core whose own editor considers parts of it a mistake.

**"GFM" now names three different things**, and anyone claiming compatibility has to say which. The first is the spec, frozen at **"0.29-gfm (2019-04-06)"**, two CommonMark revisions behind. It specifies exactly five extensions: tables, task lists, strikethrough, extended autolinks, and a raw-HTML tag filter ([GFM spec](https://github.github.com/gfm/)). The second is cmark-gfm, GitHub's open-source C implementation: the spec plus footnotes, last released in July 2023 and now receiving only security fixes ([github/cmark-gfm](https://github.com/github/cmark-gfm)). The third is what github.com actually renders: footnotes (2021), Mermaid/GeoJSON/STL fences (2022), four math syntaxes (2022–23), alerts (2023), front-matter tables, heading anchors and emoji. All of these are documented only in product docs and changelogs, with no spec text and no conformance tests ([GitHub formatting docs](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax); [GitHub math docs](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions)). The spec text even conflicts with its own reference behavior. The live spec strikes text "wrapped in a matching pair of one or two tildes," while `test/spec.txt` in the cmark-gfm repo says two. comrak in GFM mode (which mirrors cmark-gfm) strikes single-tilde `~one~`, and pandoc's `gfm` reader leaves it literal. That was re-verified with comrak 0.54 and pandoc 3.11 while writing this report ([GFM spec §6.5](https://github.github.com/gfm/#strikethrough-extension-); [cmark-gfm spec.txt](https://github.com/github/cmark-gfm/blob/master/test/spec.txt)). Engine gravity has moved as well. GitLab's backend switched from cmark-gfm to the Rust crate comrak, and Ruby's `commonmarker` gem became a comrak wrapper at v1.0 ([GitLab MR 139825](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/139825); [commonmarker](https://github.com/gjtorikian/commonmarker)). That makes comrak the closest thing to a living reference for "extended GFM."

**Obsidian Flavored Markdown is defined by a closed implementation, and that implementation is two parsers.** Obsidian's help says it "supports CommonMark, GitHub Flavored Markdown, and LaTeX" and lists about ten Obsidian-only constructs: wikilinks, embeds, block IDs, callouts, `==highlight==`, `%%comments%%`, tags, inline footnotes and YAML properties ([OFM help source](https://github.com/obsidianmd/obsidian-help/blob/master/en/Editing%20and%20formatting/Obsidian%20Flavored%20Markdown.md)). Asked for a reference spec in 2022, a moderator answered, "There is no reference spec and is not currently on the roadmap" ([Obsidian forum #29504](https://forum.obsidian.md/t/is-there-a-parser-renderer-reference-spec/29504)). An earlier researcher inspected the installed 1.13.7 desktop bundle and found a HyperMD-derived tokenizer for the editor and the *legacy, pre-micromark* remark-parse tokenizer for Reading view and Publish, each with Obsidian's tokenizers spliced in. This is primary evidence, but it rests on reading minified code. The help itself documents one place where the two disagree: inline footnotes work in Reading view but not Live Preview ([Basic formatting syntax](https://github.com/obsidianmd/obsidian-help/blob/master/en/Editing%20and%20formatting/Basic%20formatting%20syntax.md)). The largest silent divergence from CommonMark is line breaks. By default a single newline inside a paragraph renders as a visible `<br>`; the "Strict line breaks" setting turns this off ([Obsidian Settings help](https://github.com/obsidianmd/obsidian-help/blob/master/en/User%20interface/Settings.md)).

**Pandoc Markdown is the superset ancestor of the semantic features**: attributes, fenced divs, bracketed spans, citations, raw-format passthrough, definition lists and four table syntaxes. It comes from the pre-CommonMark lineage ("an extended and slightly revised version of John Gruber's Markdown syntax") and is controlled by named extensions, with `commonmark_x` as a CommonMark-based repackaging of most of them ([Pandoc MANUAL](https://pandoc.org/MANUAL.html#pandocs-markdown)). Pandoc ships roughly monthly; 3.12.1 came out 2026-10-08 ([jgm/pandoc releases](https://github.com/jgm/pandoc/releases)). Quarto and R Markdown are Pandoc Markdown with code execution on top. Quarto adds typed cross-references (`@fig-x`) and callouts as classed divs ([Quarto cross-references](https://quarto.org/docs/authoring/cross-references.html)).

**MDX is a JavaScript module format with Markdown sugar** more than a Markdown dialect. It adds JSX, `{expressions}` and ESM `import`/`export`. To make room for them it removes indented code, autolinks, raw HTML (replaced by JSX) and the ability to write a bare `<` or `{` in prose ([What is MDX](https://mdxjs.com/docs/what-is-mdx/)). Its error contract is the opposite of Markdown's: "Whereas all Markdown is valid, incorrect MDX will crash" ([mdx-state-machine](https://github.com/micromark/mdx-state-machine#72-deviations-from-markdown)). The current release is 3.1.1 (2025-08-29), and no MDX 4 has been announced ([mdx-js/mdx releases](https://github.com/mdx-js/mdx/releases)).

**Djot reads as MacFarlane's own list of CommonMark regrets turned into a language.** It is linear-time with no backtracking, its inline parsing is local, its emphasis rules are simpler, and its parsers need no Unicode classes, HTML or entity handling ([jgm/djot README](https://github.com/jgm/djot)). Its syntax is still officially **unversioned**. The site warns it "isn't completely stable yet, minor future changes to the syntax are expected," and the only numbered syntax releases are 0.1 and 0.2, both from 2022 ([djot.net](https://djot.net/); [djot changelog](https://github.com/jgm/djot/blob/main/changelog.md)). Spec-level commits since then are clarifications. Implementation work is live: MacFarlane landed djot.js performance and streaming commits in October 2026, and pandoc has read and written Djot since 3.1.12 in February 2024 ([djot.js commits](https://github.com/jgm/djot.js/commits/main); [pandoc changelog](https://github.com/jgm/pandoc/blob/main/changelog.md)).

Among the other players, **MyST** is "a superset of CommonMark" whose extension points, block *directives* and inline *roles*, are ported from reStructuredText and Sphinx ([MyST syntax overview](https://mystmd.org/guide/syntax-overview)). Its standalone spec repo was archived mid-transfer into the mystmd monorepo, with the AST spec "still in dev" ([myst-spec](https://github.com/jupyter-book/myst-spec)). **Markdoc** keeps nearly all of CommonMark (only setext headings are dropped, and indented code stays by default) and adds a single `{% … %}` construct for tags, annotations and variables. Its philosophy is "docs as data" against MDX's "docs as code" ([Markdoc FAQ](https://markdoc.dev/docs/faq)). **GitLab's GLFM** is "CommonMark core plus GFM extensions plus GitLab extensions," and is the most extended of the forge dialects: KaTeX math, titled alerts, `>>>` quotes, includes, inline diffs, and TOML or JSON front matter ([GitLab Flavored Markdown](https://docs.gitlab.com/user/markdown/)). **kramdown**, MultiMarkdown and PHP Markdown Extra are alive but in maintenance mode, and survive mainly through Jekyll and through ideas pandoc absorbed ([kramdown syntax](https://kramdown.gettalong.org/syntax.html)). **AsciiDoc** is the only markup in this comparison going through a formal standards process (Eclipse, with a spec and a compatibility kit), though no 1.0 is visible ([Eclipse AsciiDoc Language](https://projects.eclipse.org/node/19837)).

## Same glyphs, different meanings: the dialects split along three fault lines

The deviations from CommonMark come in three kinds, and the kind predicts how dangerous a dialect is to write from habit. **Additive** dialects (GFM, Obsidian, GitLab, MyST, Markdoc) keep the CommonMark core and add constructs, so CommonMark habits stay valid. **Subtractive** MDX deletes HTML, indented code and autolinks to free `<`, `{` and indentation for JSX ([MDX: What is MDX](https://mdxjs.com/docs/what-is-mdx/)). **Reinterpretive** dialects keep the glyphs and change their meaning. That describes Djot most of all, and Pandoc more mildly. In Djot, `_x_` is emphasis and `*x*` is **strong**, with no doubled delimiters. Setext headings, indented code and raw HTML are gone. Most consequentially, "Paragraphs can never be interrupted by other block-level elements," so `Groceries:` followed directly by `- milk` is one paragraph ([djot syntax reference](https://github.com/jgm/djot/blob/main/doc/syntax.md)). Pandoc requires a blank line before headings and block quotes, and its manual gives the reason: "it is all too easy for a `#` to end up at the beginning of a line by accident (perhaps through line wrapping)" ([Pandoc MANUAL, blank_before_header](https://pandoc.org/MANUAL.html#extension-blank_before_header)). Pandoc and Djot independently cite hard-wrapping as the reason for their deviations. That is convergent evidence that CommonMark's "blocks may interrupt paragraphs" rule costs real authors.

Reinterpretation produces surprises that a CommonMark-trained eye will not see coming. Earlier local tests show three, the first two re-checked with pandoc's Djot reader for this report. Djot renders `snake_case_word` as `snake<em>case</em>word`, because `_` opens and closes emphasis inside words, which is a real hazard for technical prose. Djot renders `**x**` as nested strong, not an error. Djot has no tilde fences at all, so `~~~` becomes paragraph text ([djot syntax reference](https://github.com/jgm/djot/blob/main/doc/syntax.md)). Pandoc has a mirror-image hazard: a `~~~` fence placed directly after a paragraph without a blank line turns into subscript markup ([Pandoc MANUAL, fenced_code_blocks](https://pandoc.org/MANUAL.html#extension-fenced_code_blocks)).

**Raw HTML is the deepest fault line**, giving one three-line input five readings. Take `<div>`, then `**x**`, then `</div>`, with no blank lines. CommonMark and GFM treat this as a type-6 HTML block that runs to a blank line, so the asterisks stay literal. Pandoc's default `markdown_in_html_blocks` bolds them. Obsidian explicitly "does not render Markdown syntax inside HTML elements … to keep parser complexity low." MDX parses the whole thing as a JSX element. Djot escapes the tags as literal text and nests two strongs ([CommonMark §4.6](https://spec.commonmark.org/0.31.2/#html-blocks); [Pandoc MANUAL](https://pandoc.org/MANUAL.html#extension-markdown_in_html_blocks); [OFM help](https://github.com/obsidianmd/obsidian-help/blob/master/en/Editing%20and%20formatting/Obsidian%20Flavored%20Markdown.md); [reference renderings](<../research_notes/Markdown dialect comparison/llm_familiarity_probes/reference_renderings/promptD-reference.txt>)). **Line breaks** are the quietest fault line. A single newline is a soft break in CommonMark, in GFM `.md` files and in Obsidian's strict mode. It is a hard break in GitHub issues and PRs and in Obsidian's default mode ([GitHub formatting docs](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax)). Djot has no trailing-two-spaces break at all; only backslash-newline is hard ([djot syntax reference](https://github.com/jgm/djot/blob/main/doc/syntax.md)). So "dialect" is not stable even within one vendor. The same file renders differently in a GitHub issue and a GitHub repo, and differently under Obsidian's two settings.

### A shared extension layer has formed, with collisions at the edges

Beyond the core, a de facto common layer has emerged without any spec: `[^id]` footnotes, pipe tables, `- [ ]` tasks, `> [!type]` callouts, `$`/`$$` math, and `:::` containers. The details diverge in ways that matter for interchange.

| Feature | GFM (spec / github.com) | Obsidian | Pandoc (default) | MDX (core) | Djot |
|---|---|---|---|---|---|
| Strikethrough | `~~x~~`; cmark-gfm also `~x~` | `~~x~~` | `~~x~~` | plugin | `{-x-}` |
| Highlight | — (`<mark>` HTML) | `==x==` (+ color emoji, 1.14) | `==x==` via `mark` ext. (off by default) | — | `{=x=}` |
| Sub/superscript | HTML only | HTML only | `~x~` / `^x^` (no spaces) | — | `~x~` / `^x^` |
| Footnotes | github.com only, not in spec | `[^1]`, inline `^[…]` | `[^1]`, inline `^[…]` | plugin | `[^1]` |
| Math | `$…$`, `` $`…`$ ``, `$$`, ` ```math ` | `$…$`, `$$…$$` | `$…$` (anti-currency rule), `$$` | plugin | `` $`…` ``, `` $$`…` `` only |
| Callouts | `> [!NOTE]`, 5 types, no title, no nesting | `> [!type]`, 13 types + aliases, titles, folding, nesting | `alerts` ext. | component | `::: warning` div |
| Generic container / span | — | — | `::: {#id .c}` / `[x]{.c}` | JSX | `::: c` / `[x]{.c}` |
| Attributes | — | — | headings, code, links, spans, divs | JSX props | any element |
| Wikilinks | — | `[[target\|label]]` | opt-in, either order | — | — |
| Comments | `<!-- -->` | `%%…%%` | `<!-- -->` | `{/* */}` | `{% … %}` |
| Raw passthrough | HTML (9 tags filtered) | HTML (no Markdown inside) | HTML, TeX, `{=fmt}` | none (JSX) | `{=fmt}` only |
| Citations | — | — | `[@doe99, p. 33]` | — | — |
| Definition lists | — | — | `term` / `:   def` | — | `: term` / indented def |

Sources: [GFM spec](https://github.github.com/gfm/), [GitHub formatting docs](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax), [Obsidian callouts](https://github.com/obsidianmd/obsidian-help/blob/master/en/Editing%20and%20formatting/Callouts.md), [Obsidian internal links](https://github.com/obsidianmd/obsidian-help/blob/master/en/Linking%20notes%20and%20files/Internal%20links.md), [Pandoc MANUAL](https://pandoc.org/MANUAL.html), [What is MDX](https://mdxjs.com/docs/what-is-mdx/), [djot syntax reference](https://github.com/jgm/djot/blob/main/doc/syntax.md).

The collisions are concrete. **`H~2~O`** is subscript in Pandoc and Djot, strikethrough in cmark-gfm, and literal in pandoc's `gfm` reader. **`[[a|b]]`** puts the label after the pipe in Obsidian and MediaWiki and before it in GitLab and Gollum wikis, so comrak and Pandoc each ship both orders as separate options ([GitLab docs](https://docs.gitlab.com/user/markdown/); [Pandoc MANUAL](https://pandoc.org/MANUAL.html#extension-wikilinks_title_after_pipe)). **`{% … %}`** is a comment in Djot but a tag in Markdoc, Liquid and Jinja ([Markdoc syntax](https://markdoc.dev/docs/syntax)). **`{+x+}`** means insertion in both Djot and GitLab, but the deletion forms differ (`{-x-}` against `[-x-]`). **Math is the least interoperable common feature**. It differs on four axes: the delimiter set, the tokenizing rule (micromark's code-span-like dollar counts, pulldown-cmark's greedy left-to-right, Pandoc's flanking-plus-no-digit rule, GitHub's undocumented behavior), whether `$$` may appear inline, and MathJax against KaTeX. comrak now exposes `$`-math, GitHub's backtick math and `\(…\)` LaTeX math as three separate flags ([comrak options](https://github.com/kivikakk/comrak/blob/main/src/parser/options.rs); [pulldown-cmark math spec](https://github.com/pulldown-cmark/pulldown-cmark/blob/master/pulldown-cmark/specs/math.txt)).

**Callouts are the most successful recent convergence, and their lineage is longer than it looks.** The `> [!NOTE]` syntax first appears in Microsoft's DocFX Flavored Markdown spec in a commit dated **2015-12-10** ([dotnet/docfx history](https://github.com/dotnet/docfx/commits/main/Documentation/spec/docfx_flavored_markdown.md)). Obsidian's 0.14.0 release (2022-03-14) says its callouts were "inspired by the 'alert' syntax from Microsoft Docs" ([Obsidian v0.14.0 changelog](https://obsidian.md/changelog/2022-03-14-desktop-v0.14.0/)). GitHub shipped the same five type names in December 2023 ([GitHub changelog](https://github.blog/changelog/2023-12-14-new-markdown-extension-alerts-provide-distinctive-styling-for-significant-content/)), and the GitHub subset has since spread to Typora, Bear, HackMD, VitePress, Pandoc, comrak and pulldown-cmark. The convergence is real but shallow. Obsidian's callouts are a strict superset of GitHub's: titles, `+`/`-` folding, 13 types, and case-insensitive `important` and `caution` as aliases where GitHub has distinct types ([Obsidian callouts](https://github.com/obsidianmd/obsidian-help/blob/master/en/Editing%20and%20formatting/Callouts.md)). The GitHub subset is therefore the safe interchange form. A reader without support sees a block quote that starts with a literal `[!NOTE]`.

**The `:::` fence has converged on "named block container"; what follows it has not.** Pandoc wants mandatory `{attributes}`. Djot takes one bare class word and puts other attributes on the line above. MyST puts a *directive name* with arguments there. Docusaurus and Starlight use remark-directive's `:::name[label]{attrs}`. VitePress uses a free-text title ([Pandoc MANUAL, fenced_divs](https://pandoc.org/MANUAL.html#extension-fenced_divs); [MyST syntax overview](https://mystmd.org/guide/syntax-overview); [remark-directive](https://github.com/remarkjs/remark-directive); [VitePress Markdown](https://vitepress.dev/guide/markdown)). The generic-directives proposal behind remark-directive has been open on the CommonMark forum since 2014 with no maintainer ruling ([talk.commonmark.org](https://talk.commonmark.org/t/generic-directives-plugins-syntax/444)). The strongest convergence of all is the **`{#id .class key=val}` attribute grammar**, shared verbatim by Pandoc, Djot, Quarto and MyST's inline options. kramdown differs only by a `{:` prefix.

### Four extension models, and a drift toward strictness

The dialects take four approaches to going beyond a fixed feature set. Each approach implies a different error contract.

1. **Closed enumeration with HTML as the escape hatch:** CommonMark, GFM, Obsidian.
2. **Generic attributes and containers interpreted later by filters:** Pandoc and Djot. Djot is the purest case: "No expressive blind spots," and no built-in semantics for classes or symbols ([jgm/djot README](https://github.com/jgm/djot)).
3. **Named directives or tags:** MyST, Markdoc, GitLab's `::include{…}`.
4. **An embedded host language:** MDX.

Every Markdown-lineage dialect is *total*: any input yields a document. MDX is *partial* and crashes on bad input. The notable 2025–26 development is that Pandoc's own heaviest user is moving toward partiality. Quarto's experimental Rust parser, quarto-markdown, "gives syntax errors in malformed documents" and calls CommonMark's "Any sequence of characters is a valid CommonMark document" "not … tenable … in large documents." It also drops naked HTML in favor of `{=html}`, which is Djot's stance ([quarto-dev/quarto-markdown](https://github.com/quarto-dev/quarto-markdown); [quarto-dev/q2](https://github.com/quarto-dev/q2)). Three of the most-engineered toolchains (Djot, MDX, Quarto's next parser) have each removed or fenced the same CommonMark features: raw HTML, indented code, lazy or non-local structure. "Forgiving by design" is losing favor among implementers, while authors and LLMs keep writing forgiving Markdown.

There is a parsing-cost side to this. CommonMark's linear time is an achievement of careful implementation, not a property of its grammar. cmark carries a whole suite of pathological inputs, and cmark-gfm had four 2023 CVEs for polynomial blow-ups ([cmark pathological tests](https://github.com/commonmark/cmark/blob/master/test/pathological_tests.py); [CVE-2023-26485](https://stack.watch/vuln/CVE-2023-26485)). An earlier local benchmark found pandoc's default `markdown` reader **exponential on 40 bytes of unclosed `[`**, traced to the default `citations` extension. It also found djot.js linear on the same pathological shapes, while pandoc's Haskell Djot reader was roughly quadratic on two link patterns. That last result points to an implementation cost, not one in Djot's grammar ([pandoc](https://github.com/jgm/pandoc); [djot.js](https://github.com/jgm/djot.js)).

## GFM-flavored CommonMark outnumbers every rival by one to five orders of magnitude

Dialects do not map one-to-one onto packages. Most parsers implement CommonMark plus GFM extensions, so the two cannot be separated at the library level. Obsidian has no parser package of its own, and download counts include CI and transitive pulls. With those caveats, the orders of magnitude are unambiguous.

The scale order is **GFM/CommonMark ≫ Pandoc family ≈ MDX > Obsidian ≫ MyST ≈ Markdoc ≫ Djot**, with the middle tier serving different populations. Pandoc and MDX are comparable in size but share almost no users: one is scientific and academic publishing, the other JS documentation. Obsidian's authoring population is large but nearly invisible in public file counts because vaults are private. Its user count is genuinely unknown. A secondary source reports about 1.5M active users and about $25M ARR ([Tech Insider](https://tech-insider.org/obsidian-vs-notion-2026/)). The CEO guessed "around 5–10 million people but I'm not sure" ([kepano on Mastodon](https://mastodon.social/@kepano/114871343744754732)). A single desktop release drew 1.84M in-app update downloads in about two months, which suggests an installed base in the low millions at least. GFM's reach is set by GitHub's 180M+ developers and multiplied by LLM chat interfaces, whose dominant open-source rendering stacks are GFM by construction. Vercel's Streamdown "includes full support for GitHub Flavored Markdown" ([streamdown docs](https://streamdown.ai/docs/gfm)).

**Djot is tiny on every axis.** Its npm package draws about 1/58,000 of `marked`'s downloads. PyPI shows 46 downloads a month. Its VS Code extensions have a few hundred installs, Stack Overflow has no `djot` tag, and 42 GitHub repositories carry the `djot` topic ([GitHub topic search](https://api.github.com/search/repositories?q=topic:djot); [SE tags API](https://api.stackexchange.com/2.3/tags/djot/info?site=stackoverflow)). Its only mid-sized number is 2,044 GitHub stars, which measures attention to MacFarlane more than use. The one rising Djot figure, Rust `jotdown` downloads, is transitive pull from two RAG document-extraction crates (`kreuzberg`, `xberg`), not people authoring Djot. The Djot-authoring crates `mdbook-djot` and `djot-ssg` drew 38 and 21 downloads over 90 days ([jotdown reverse dependencies](https://crates.io/api/v1/crates/jotdown/reverse_dependencies)). Djot does have a small, real ecosystem independent of its author. It covers PHP (djot-php, phpDocumentor, a WordPress plugin), Go, Rust and the SILE typesetter, and pandoc gives it free conversion to every pandoc format ([phpDocumentor guides-djot](https://github.com/phpDocumentor/guides-djot); [pandoc changelog](https://github.com/jgm/pandoc/blob/main/changelog.md)).

Several platforms sit outside the six named dialects but carry large populations. **MkDocs** (Python-Markdown plus pymdown-extensions) draws 13.5M PyPI downloads a month, and Python-Markdown itself 93M, mostly through MkDocs ([pypistats mkdocs](https://pypistats.org/api/packages/mkdocs/recent)). Microsoft Learn runs CommonMark through Markdig with DocFX extensions ([Microsoft Learn Markdown reference](https://learn.microsoft.com/en-us/contribute/content/markdown-reference)). Stack Exchange moved its whole network to CommonMark in 2020 ([Meta Stack Exchange, mirror](https://backiee.wasmer.app/https_meta_stackexchange_com/a/349119)). Outside Markdown, reStructuredText has about 8.7M files on GitHub, AsciiDoc 1.54M, and Typst 56.6k GitHub stars, more than pandoc's 46.6k ([GitHub code search](https://api.github.com/search/code?q=extension:rst); [typst repo](https://api.github.com/repos/typst/typst)). Chat dialects (Slack mrkdwn, Discord, Reddit) share Markdown's look but not its grammar. Slack's bold is a single `*` ([Slack formatting docs](https://docs.slack.dev/messaging/formatting-message-text)).

## Normalized for npm's 2026 surge, GFM and Obsidian gain while MDX and Djot stall

Every Markdown package grew in absolute downloads, and that number on its own means almost nothing. **npm as a whole roughly tripled between September 2025 and September 2026** (`typescript` 2.9×, `react` 3.8×) and grew about 8–10× from 2022, a steady ramp that third-party analysis attributes to CI and coding agents rather than people ([npm range API](https://api.npmjs.org/downloads/range/2025-03-01:2026-09-30/react); [amplifying.ai](https://amplifying.ai/coding-agents/npm)). The cause is not established from a primary source, so growth relative to these baselines is the only safe reading.

| Package (dialect role) | Sep 2022 → Sep 2026 | Sep 2025 → Sep 2026 |
|---|---|---|
| *baseline: typescript / react* | *7.9× / 10.1×* | *2.9× / 3.8×* |
| `remark-gfm` (GFM layer) | **41×** | 5.3× |
| `react-markdown` (chat/UI rendering) | **25×** | 5.1× |
| `streamdown` (AI-chat renderer, GFM) | new (Aug 2025) | **49×** |
| `turndown` (HTML→Markdown) | 19× | 4.8× |
| `marked` (GFM default) | 12× | 4.5× |
| `micromark` (CommonMark core) | 15× | 3.8× |
| `markdown-it` | 8.6× | 2.7× |
| `@mdx-js/mdx` (MDX compiler) | **2.7×** | 3.5× |
| `commonmark` (commonmark.js reference) | 2.1× | **0.8×** |
| `@markdoc/markdoc` | 78× (from 30k/mo) | 4.6× |
| `@djot/djot` | ~200/mo (2023) → ~4k/mo | ~4× |

Source: [npm downloads API](https://api.npmjs.org/downloads/point/2022-09-01:2022-09-30/react), point queries per package and month, pulled 2026-10-14.

**GFM is becoming the default even inside "pure CommonMark" stacks.** Within unified/remark, `remark-gfm` downloads as a share of `remark-parse` rose from **11% (2022) to 25%, 40%, 55% and 77% (2026)**. That is the cleanest dialect-level signal any registry offers: users of one parser ecosystem choosing the GFM superset over plain CommonMark ([npm downloads API](https://api.npmjs.org/downloads/point/2022-09-01:2022-09-30/remark-gfm,remark-parse)). The fastest growers share a role: rendering Markdown that LLMs produce (`react-markdown`, Streamdown) and converting the web into Markdown that LLMs consume (`turndown` on npm, and `markdownify` on PyPI at about 350× since 2022). Markdown has become the interchange format between people, documents and models. That channel is GFM-shaped. Cloudflare's "Markdown for Agents" now converts HTML to Markdown at the edge for clients that send `Accept: text/markdown` ([Cloudflare docs](https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/)), and GitHub code search finds about 1.04M `AGENTS.md`, 0.88M `CLAUDE.md` and 191k `llms.txt` files ([GitHub code search API](https://docs.github.com/rest/search/search#search-code)). The causal link from LLMs to these packages is inferred from what the packages do; no source measured it.

**Attention to Markdown in general is at a record high.** "Markdown" appears in 1,829 of every million Hacker News comments in 2026 to date, against 1,082 in 2022 ([ClickHouse HN mirror](https://sql-clickhouse.clickhouse.com/?user=demo)). Stack Overflow's survey shows "Markdown File" as a documentation tool rising from about 26% of respondents (2023) to 29% (2024) and **34.8% (2025)**, ahead of Confluence's 32.8% ([SO 2023](https://survey.stackoverflow.co/2023/); [SO 2024](https://survey.stackoverflow.co/2024/technology); [SO 2025](https://survey.stackoverflow.co/2025/technology/)). The survey samples shrank each year, so the rise is suggestive, not rigorous.

**CommonMark won as a substrate and lost as a brand.** CommonMark-conformant engines are everywhere (micromark, markdown-it, markdown-it-py, pulldown-cmark, comrak, goldmark, Markdig). Meanwhile commonmark.js, the reference JS implementation, is falling in absolute terms, from 4.07M to 3.13M a month, and per thousand `react` downloads it went from 20 to 4. People adopt "Markdown," meaning CommonMark plus GFM, and few choose plain CommonMark.

**MDX is entrenched but not spreading.** Measured against `react`, `@mdx-js/mdx` fell from 234 downloads per thousand in 2022 to 63 in 2026, and its 2022 absolute figure was higher than 2023's or 2024's ([npm downloads API](https://api.npmjs.org/downloads/point/2022-09-01:2022-09-30/react)). Its repository's yearly star events fell from 4,451 (2018) to 1,728 (2024). The MDX-based docs frameworks are healthier: Docusaurus core kept pace with the baseline (9× since 2022), and the newer Starlight and Fumadocs grew 12× and 15× in the last year alone, against a baseline of about 3×. MDX is held in place by its install base, not by new adoption beyond it. Its cost is documented: Docusaurus called the MDX 1→3 upgrade "the main challenge to the adoption of Docusaurus v3," with fixes "often related to `{` and `<` characters that you now need to escape" ([Docusaurus 3.0](https://docusaurus.io/blog/releases/3.0)). **Markdoc** grew 78× but from a tiny base, and is about 5% of MDX's compiler downloads. Its GitHub stars peaked at launch (5,383 star events in 2022, 625 in 2024).

**Obsidian is the strongest growth signal outside GFM.** Release-asset downloads, which include the desktop app's in-app update files and so act as an active-install proxy, run 5.8M (2022), 11.2M (2023), 15.9M (2024), 23.9M (2025) and already **31.5M in 2026 by mid-October**, 32% above all of 2025 ([obsidian-releases API](https://api.github.com/repos/obsidianmd/obsidian-releases/releases)). Its Stack Overflow survey share rose from 13% (2024) to 16.1% (2025), and Hacker News mentions have held a high plateau of about 1.7–2.0k comments a year since 2022. Obsidian's community plugin directory more than doubled after a May 2026 relaunch, to over 8,000 projects ([Obsidian blog, Oct 2026](https://obsidian.md/blog/2026-obsidian-october/)). Because OFM is a superset of CommonMark plus GFM, Obsidian's growth also reinforces GFM as the base layer.

**The Pandoc family is stable at the core and reshuffling on top.** Pandoc itself is steady: 350–480 HN comments a year for a decade, and 6.9M release-asset downloads for 2025's releases ([jgm/pandoc releases API](https://api.github.com/repos/jgm/pandoc/releases)). Inside the family, **Quarto replaced R Markdown**. Quarto CLI release downloads went 0.91M (2022), 1.98M, 5.66M, 6.89M (2025). Quarto overtook `r-markdown` in new Stack Overflow questions in 2024, and `.qmd` files (848k) are near parity with `.Rmd` (1.05M) after six years against R Markdown's twelve ([quarto-cli releases API](https://api.github.com/repos/quarto-dev/quarto-cli/releases); [Stack Exchange API](https://api.stackexchange.com/2.3/questions?site=stackoverflow&tagged=quarto&filter=total)). Quarto's own HN attention peaked in 2024 (177 comments) and has since fallen (52 in 2026 to date). Posit announced a Rust rewrite, Quarto 2, for late 2026 ([Wikipedia: Quarto](https://en.wikipedia.org/wiki/Quarto_(software))). Pandoc Markdown as an *authoring* dialect is consolidating under Quarto, while most pandoc installs are for format conversion.

**MyST** grows modestly above baseline (`myst-parser` 7.3× since 2022 against numpy's 5.9×). Jupyter Book 2, rebuilt on the MyST engine, is its main vehicle ([SciPy 2025 talk](https://cfp.scipy.org/scipy2025/talk/NYPUVH/)). **kramdown**, MultiMarkdown, showdown and R Markdown are fading on every attention measure. **Typst** is the breakout outside Markdown, at 24 HN comments in 2022 and 754 in 2025, and Quarto and Jupyter Book 2 both support it for PDF output ([UC ANR](https://ucanr.edu/node/115337); [SciPy 2025 talk](https://cfp.scipy.org/scipy2025/talk/NYPUVH/)). **Djot** shows no inflection. Its npm downloads rose from about 200 to about 4,000 a month over three years, star events peaked at its 2022 launch (994) and then fell to a few hundred a year, and its HN mentions run 10–40 a year. Several trend sources are missing. Google Trends was not retrievable. The GH Archive star mirror degrades after mid-2025. Stack Overflow is no longer a usable signal, since its total question volume fell about 99% between 2020 and 2026.

## Named, every dialect is writable by frontier models; unnamed, they all write the same hybrid

Two independent probe batteries were run on 2026-10-14 from Joseph's machine. Both removed his CLAUDE.md and estate context, a step that turned out to be necessary, and disabled tools wherever the CLI allowed it. Outputs were graded with real parsers: djot.js, pandoc 3.11, `@mdx-js/mdx`, `@markdoc/markdoc`, myst-parser, kramdown 2.5.2, asciidoctor.js and commonmark.js. The first battery covered eight models with 16 prompts each. Those prompts were recognition of unlabeled snippets, a 22-question trap quiz, writing the same 12-element document in each of eleven dialects, and unprompted defaults ([probe README](</Users/josephwecker-v2/.archive/udon-more-markdown-primed-2026-10-14/spike-dir/research_notes/Markdown dialects landscape/llm_probes/README.md>)). The second covered five models with four prompts, one of them a set of ten snippets whose meaning depends on the dialect ([second-battery prompts](<../research_notes/Markdown dialect comparison/llm_familiarity_probes/promptD.txt>)). Each cell is a single sample. No GPT-5.x or Gemini Pro model was reachable: the Codex CLI was over its usage limit, the Gemini CLI is deprecated for individual accounts, and the first battery used up the Gemini Flash quota. gpt-oss-120b, an open-weights model, is the only OpenAI-lineage data point.

Gemini's Markdoc, kramdown and AsciiDoc cells are missing because of the quota.

The second battery agrees on the shape. Asked to write 16 Djot features, Sonnet and Opus produced documents in which **all 16 render correctly in djot.js**, including converting `**bold** and *italic* and ~~gone~~` to `*bold* and _italic_ and {-gone-}`. Haiku scored 15/16, misplacing a table caption. Grok scored about 11/16, and every miss was a Pandoc construct carried into Djot: `# Heading {#id}`, `$x^2$`, Pandoc definition lists, `::: {.warning}` and `Table: caption`. gpt-oss scored about 5/16, claiming that "Djot uses the same syntax" as CommonMark while rating its own Djot confidence 4 of 5 ([Opus output](<../research_notes/Markdown dialect comparison/llm_familiarity_probes/outputs/claude-opus-A.txt>); [Grok output](<../research_notes/Markdown dialect comparison/llm_familiarity_probes/outputs/grokclean-A.txt>); [gpt-oss output](<../research_notes/Markdown dialect comparison/llm_familiarity_probes/outputs/agy-gptoss120b-A.txt>)). The two batteries disagree on one cell, and the disagreement is itself informative. In the second run Haiku named both Djot snippets correctly; in the first it called Djot "Pandoc Markdown," with a confabulated explanation. Djot recognition sits right at Haiku's edge and flips between samples. The same was true for every other dialect in the set. CommonMark spec facts (seven HTML-block kinds, the rule that only lists starting at 1 interrupt a paragraph), the GFM spec-versus-github.com boundary, Pandoc citations, MDX's removals, MyST directives and Markdoc tags were all answered correctly by the Claude 5.x models and Grok ([second-battery notes, outputs](<../research_notes/Markdown dialect comparison/llm_familiarity_probes/outputs/>)).

**The failures are interference, not ignorance.** Haiku and Grok explain Djot's rules correctly when quizzed and still *write* Pandoc's `# Heading {#id}` in Djot, a form djot.js reports as "Ignoring unattached attribute." The heading never gets its id, so a "back to top" link points nowhere ([Haiku Djot render](</Users/josephwecker-v2/.archive/udon-more-markdown-primed-2026-10-14/spike-dir/research_notes/Markdown dialects landscape/llm_probes/raw/claude-haiku-5-5/g_djot.rendered.html>)). The leaks are always the same few habits: Pandoc's heading attribute, Markdown's `**` and `$…$`, `==` highlights, and GFM fences and task lists. **Supersets of GFM absorb these habits harmlessly**, which is why Obsidian, Pandoc, Quarto and MyST were written well by every model except gpt-oss. **Dialects that reassign or reject familiar syntax break, and they break in two ways.** MDX fails loudly. Sonnet 4.6 and gpt-oss both opened with `# Release Notes {#release-notes}`, and the whole document fails with "Could not parse expression with acorn" ([Sonnet 4.6 MDX output](</Users/josephwecker-v2/.archive/udon-more-markdown-primed-2026-10-14/spike-dir/research_notes/Markdown dialects landscape/llm_probes/raw/agy-claude-sonnet-4-6/g_mdx.md>)). Djot and AsciiDoc fail silently. In Djot, `*important*` renders bold, `$x$` stays literal, and a stray attribute is dropped with only a warning. In AsciiDoc, five of seven models wrote `*stable*footnote:[…]`, which Asciidoctor renders with literal asterisks because constrained bold must be followed by a non-word character ([Haiku AsciiDoc render](</Users/josephwecker-v2/.archive/udon-more-markdown-primed-2026-10-14/spike-dir/research_notes/Markdown dialects landscape/llm_probes/raw/claude-haiku-5-5/g_asciidoc.rendered.html>)). The same failure shows up in production. A Fern docs build broke when `{API name}` in LLM-written changelog prose was parsed as a JSX expression ([fern-api/docs#2065](https://github.com/fern-api/docs/pull/2065)).

**Pandoc acts as an attractor.** Every model that misidentified Djot called it Pandoc, and gpt-oss also called kramdown's `{: .lead #intro}` "Pandoc Markdown." This happened even though kramdown is widely deployed through Jekyll and GitHub Pages ([GitHub Pages docs](https://docs.github.com/en/pages/setting-up-a-github-pages-site-with-jekyll/setting-a-markdown-processor-for-your-github-pages-site-using-jekyll)). Unfamiliar `{…}`-attribute syntax gets pulled toward the best-documented brace dialect.

**Self-assessment carries no information at the dialect level.** Every model rated CommonMark and GFM 4–5 and Djot about 3, whether its measured Djot knowledge was 1/5 or 5/5. The Claude models underrated themselves on Djot (rating 3 while scoring 15–16 of 16). gpt-oss and Gemini overrated themselves. Specific "unsure" flags from the strong models did cluster where they were weak, such as Djot caption syntax and MDX release dates, so construct-level hedges are informative even when dialect-level ratings are not ([quiz transcripts](</Users/josephwecker-v2/.archive/udon-more-markdown-primed-2026-10-14/spike-dir/research_notes/Markdown dialects landscape/llm_probes/raw/>)).

### Unprompted defaults: an unnamed "maximal Markdown"

Asked for a short note with math, a warning box, a table, a footnote and a highlight, with no dialect named, **all 15 usable samples from eight models** used pipe tables, `[^n]` footnotes and a `> [!WARNING]` alert. None used Pandoc, Djot or MyST constructs ([default-emission summary](</Users/josephwecker-v2/.archive/udon-more-markdown-primed-2026-10-14/spike-dir/research_notes/Markdown dialects landscape/llm_probes/default_emission_summary.txt>)). The splits follow vendor lineage. Claude and Gemini write `$…$` / `$$…$$`. Grok and gpt-oss write ChatGPT's `\(…\)` / `\[…\]`, which many dollar-only renderers do not parse and which receivers repair with preprocessors ([assistant-ui LaTeX guide](https://www.assistant-ui.com/docs/guides/latex); [OpenAI community](https://community.openai.com/t/request-delimiter-support-for-ai-generated-content-in-discourse-math-latex/1120810)). Highlights split between `==…==` and `<mark>` with no lineage pattern. Given ten ambiguous snippets, models chose a **union of the most popular readings**. They took CommonMark for the core (`*x*` is emphasis, a list interrupts a paragraph, an HTML block swallows `**x**`), GFM for autolinks, Pandoc for `H~2~O`, `^[note]` and definition lists, and Obsidian's order for `[[a|b]]`. No model chose the Djot reading of any glyph. None mentioned that `{% %}` is a Djot comment or that Djot makes `*x*` strong, even though the same models write Djot flawlessly when asked ([Opus readings](<../research_notes/Markdown dialect comparison/llm_familiarity_probes/outputs/claude-opus-D.txt>); [reference renderings](<../research_notes/Markdown dialect comparison/llm_familiarity_probes/reference_renderings/promptD-reference.txt>)). Asked to pick a format freely for a notes document, Haiku and Opus chose Obsidian-flavored Markdown. The clean Grok run chose AsciiDoc. The prompt mentioned a "notes collection," which biases toward Obsidian.

This default is closer to what **Obsidian** renders than to any published spec. Obsidian accepts GFM tables and footnotes, `$` math, `[!WARNING]` callouts and `==`; github.com renders all of these except `==`. The `> [!WARNING]` convergence shows how fast a syntax popularized by one large renderer becomes every model's default: DocFX in 2015, Obsidian in 2022, GitHub in late 2023, and universal model behavior by 2026. Independent practitioner evidence agrees. LangChain's frontend guide recommends enabling GFM because its features "are commonly used by LLMs," and `breaks: true` because "LLMs often use single newlines for visual separation" ([LangChain docs](https://docs.langchain.com/oss/javascript/langchain/frontend/markdown-messages)). Vendors say little officially. Anthropic's claude.ai system prompt for Sonnet 4.5 told the model to "use CommonMark standard markdown" for bullet points, while the Opus 5.5 prompt names no dialect ([Sonnet 4.5 system prompt](https://platform.claude.com/docs/en/release-notes/system-prompts/claude-sonnet-4-5); [Opus 5.5 system prompt](https://platform.claude.com/docs/en/release-notes/system-prompts/claude-opus-5-5)). OpenAI's reasoning models in the API "avoid generating responses with markdown formatting" unless re-enabled ([OpenAI reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices)).

### Published evidence treats Markdown as one thing

No published benchmark measures LLM competence per Markdown dialect. MDEval measures generic "Markdown awareness" across 20K instances ([arXiv 2501.15000](https://arxiv.org/abs/2501.15000)). StructEval covers 18+ structured formats without splitting Markdown by dialect ([arXiv 2505.20139](https://arxiv.org/abs/2505.20139)). LatentMD finds that **38% of valid outputs are "content-correct but boundary-broken,"** driven by "same-family symmetric-delimiter collisions" such as nested backtick fences, which is a CommonMark-level problem rather than a dialect one ([arXiv 2609.06993](https://arxiv.org/abs/2609.06993)). A March 2026 community eval of eight models found frontier models passing nearly every GFM-feature test. Its failures were single-tilde strikethrough, non-standard footnotes and backtick escaping ([thibaudcolas gist](https://gist.github.com/thibaudcolas/57dec97ef6d7b65591addda1b42139d8)). The dialect-specific evidence is practical, not academic. Obsidian's CEO maintains an agent skill teaching Obsidian Flavored Markdown, with **about 49.5k stars**, which covers "only Obsidian-specific extensions — standard Markdown … is assumed knowledge" ([kepano/obsidian-skills](https://github.com/kepano/obsidian-skills); [obsidian-markdown SKILL.md](https://github.com/kepano/obsidian-skills/blob/main/skills/obsidian-markdown/SKILL.md)). Claude skills also exist to sanitize LLM-written MDX ([mdx-sanitizer](https://www.skills.sh/erichowens/some_claude_skills/mdx-sanitizer)).

**Familiarity tracks uptake only below the frontier.** Ranked by footprint, the popularity data predicts familiarity in the order GFM ≈ CommonMark, then MDX and Obsidian, then the Pandoc family, AsciiDoc, Markdoc/MyST/kramdown, and Djot last. The probes support that ordering only as a ranking of *which dialect weaker models fail first*. Djot is about 30,000 times rarer than `.md` by file count, yet Opus, Sonnet and Fable write it without error. kramdown is widely deployed, yet a weaker model folded it into Pandoc. A better predictor of competence than deployment is the amount of *distinctive, explained* syntax in circulation. Djot has a small, regular spec written by the author of CommonMark and pandoc, and the pandoc MANUAL has been quoted for twenty years. Most `.mdx` and kramdown files contain mostly plain Markdown, so they add little distinctive signal. Deployment does matter for defaults and tie-breaking, which follow the vendor's renderer and the largest platform. This explanation is an inference from the probe pattern. Base-model familiarity, which would track training ratios more directly, was not measured.

## Conclusion

The question "which dialect is most popular and best known to LLMs" turns out to have two answers that diverge. On usage and default behavior there is no contest. The living standard is an unnamed "CommonMark core + GitHub surface conventions + `$` math + `> [!TYPE]` callouts," which no spec defines, whose most complete open implementation is comrak rather than anything GitHub publishes, and which LLMs emit and Obsidian renders more completely than github.com does. On *capability*, the frontier has made dialect familiarity a non-issue: any dialect with a small, well-explained spec can be written correctly by the strongest current models when the dialect is named in context. The risk that remains is not ignorance but interference: habits from GFM and Pandoc leaking into dialects that give familiar glyphs new meanings. How costly that risk is depends on the failure mode. Supersets absorb the slip, MDX crashes on it, and Djot and AsciiDoc render it wrong in silence. That axis (absorb, crash, or silently misrender) is a more useful lens for comparing dialects than raw familiarity scores, and no published benchmark has measured it.

The trend lines also point in a direction the popularity numbers hide. Authors and models keep writing forgiving GFM-shaped Markdown in growing volume, while the most heavily engineered toolchains move the other way. Djot, MDX and Quarto's next-generation parser each removed raw HTML, indented code and non-local structure, and two of them turn malformed input into errors. CommonMark's spec has stopped moving, GFM's spec stopped in 2019, and Obsidian declines to write one, so the practical definition of "Markdown" now lives in implementations and model behavior rather than in documents. The open gaps that most limit these conclusions are GPT-5.x and Gemini Pro probes, repeated sampling to measure the run-to-run variance already visible at Haiku's tier, a test of whether a file extension alone (`.dj` against `.md`) switches a model's defaults, and Google Trends data for the attention curves.
