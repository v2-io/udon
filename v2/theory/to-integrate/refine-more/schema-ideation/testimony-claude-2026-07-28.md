Here's my honest, unresearched take — genuinely from the seat of someone who lives inside config files, data files, and long documents all day, usually through a diff view or a narrow edit tool, usually inferring conventions from whatever's around me rather than consulting a spec.

**1. What I'd hope a schema-layer analysis covers, and what would disappoint me if unasked**

The question I most want asked first is not "what constraint language should we use" but "what is a schema *for*, in this format, given that documents mix prose and structure freely?" That's not a rhetorical throat-clear — it's the actual fork in the road. In JSON/YAML-land, "schema" almost always means "validate this data before a machine consumes it." But a format that's explicitly trying to be Markdown-and-YAML-and-XML-at-once is going to have documents that are 80% prose with a little structured skeleton, and documents that are 80% structured data with a little narrative gloss, existing as first-class citizens of the *same* schema question. I'd be disappointed if the analysis assumed the JSON-Schema framing (validate a data shape) and never asked the harder question: does a schema here also need to say something about *document shape* — required sections, ordering, prose-vs-structure ratios, where free text is allowed to appear versus where it's forbidden? If the answer is "no, schema is purely for the structured islands, prose is always exempt," that's a legitimate and clean answer — but it has to be a stated decision, not a silent default inherited from JSON Schema's ancestry.

Second thing I'd hope gets asked: who is the schema *for* — a human author, a validator/CI process, an editor doing autocomplete, or an agent generating/patching documents? These have really different needs and I have direct scars from formats that picked one implicitly and made the others painful (see GraphQL SDL below — beautifully suited to codegen and editor tooling, much less suited to "what does an ad hoc client actually need to send"). I'd want the analysis to explicitly enumerate these consumers and score each schema design against each one, rather than picking a "schema language" and assuming it serves everybody.

Third: migration and evolution. A schema born on day one is invariably wrong or incomplete by month three. I'd be disappointed if versioning, deprecation, and "what happens to a document written against v1 when the schema is now v2" isn't a first-class section rather than a footnote. This is where Rails migrations and Ash resources earned my trust and JSON Schema mostly hasn't (more below).

Fourth: I'd want the analysis to be honest that "schema" is being asked to do at least four distinct jobs that other ecosystems keep separate — (a) validate/constrain, (b) document/describe for humans, (c) drive tooling (autocomplete, codegen, diffing), (d) own and migrate the data over time. Most schema systems I've used picked one or two of these and bolted the others on badly. I'd want to see the analysis name this rather than assume "a schema" is one coherent thing.

**2. Pains I actually know first-hand**

JSON Schema: helped me enormously for editor autocomplete and CI validation gates — genuinely good at "reject the malformed document before a human wastes time on it." But the failure mode I've hit over and over is *silent semantic drift*: a schema says a field is `string`, and that's true, but it tells me nothing about what the string *means*, what format variants are acceptable, or what happens if I get it almost-right. `oneOf`/`anyOf`/`allOf` composition is where I've lost the most hours — validators give error messages that enumerate every branch that failed, and as the human or agent editing the document I get a wall of contradictory-sounding errors instead of "you probably meant this branch, and here's specifically what's wrong with it." That's a UX failure baked into the constraint-language design, not an implementation bug — disjunctive constraint languages fundamentally struggle to explain "which branch did you mean."

XSD: I mostly experienced this as punishment. Verbose to write, verbose to read, and the namespace story compounds the pain — I have genuinely given up trying to hand-author XSD-conformant XML and instead copy an example and pray. That's actually a useful data point: when a schema language is hard enough to author against directly, everyone reverts to "copy a known-good example and pattern-match," which is its own kind of schema (see below) — an unintentional one, adopted because the intentional one was too costly to use directly.

Protobuf: field numbers as the versioning mechanism is simple and I respect it, but the "everything is optional/has a default, there's no real way to express `required` without pain" problem bit me concretely — I've received messages that parse cleanly and are semantically garbage because a field that should have been mandatory was silently absent-and-defaulted. The schema *validated* and was *wrong*. That's the worst kind of failure for a schema to permit: passing validation while being substantively broken.

CUE: this is the one that genuinely delighted me, and I want to be specific about why. Values-and-constraints unify — a schema is just a partial value, and a fully-specified value is a valid instance of its own schema. That collapses "the example" and "the constraint" into one artifact, which is exactly the kind of unification I'd want an analysis to take seriously for this format, because your format already has a strong "the example is often the best doc" instinct. The awkwardness I hit with CUE was tooling maturity and the mental model of lattices/unification being genuinely hard to build intuition for when things go wrong — error messages sometimes point at a unification conflict three files away from where I was actually editing.

Dhall: total, non-Turing-complete config language, imports resolved by hash. I respected the principle (no surprises, reproducible) and hated the friction — writing let-bindings and explicit types for what should have been "here's a list of strings" was a tax I paid on every file. It taught me that safety-by-construction has a real authoring-cost line, and past that line people write the equivalent config in something looser and generate the Dhall, defeating the purpose.

Rails/ActiveRecord migrations, and especially Ash resources: this is the one I'd hold up as the most different *kind* of thing from the others, and I've had the best experience with it for exactly the reason you flagged — the class IS the schema, and it owns responsibility for moving data between its own past and present shape. The pain with plain Rails migrations is that the migration history and the "current shape" can drift into two sources of truth (schema.rb vs. the accumulated migrations) and reconstructing "what does this column actually mean now" requires archaeology. Ash tightens this by making the resource itself the single place validations, transformations, and relationships live, and I've found that dramatically better for long-lived data — but it only works because Ash resources are executable code with real behavior, not a static description. That's a big tell: the "owns migration" super-power seems to require the schema to be able to *run*, not just *describe*. A static description language (JSON Schema, XSD) structurally cannot do this without inventing a whole separate migration DSL bolted alongside it — which is exactly what most ecosystems end up doing (Rails migrations *are* that bolted-on DSL, separate from the model classes).

GraphQL SDL: fantastic for codegen and the specific case of "client asks for exactly the shape it needs," miserable the one time I needed to express "these two fields are mutually exclusive" or "this is valid only if that other field has this value" — cross-field conditional constraints are just not in SDL's vocabulary and everyone ends up hand-rolling resolver-level validation that isn't visible in the schema at all. That invisibility is the real cost: the schema *looks* authoritative and complete but has a shadow layer of constraints living in code that no tool can see.

Tree-sitter grammars: technically not a data schema but structurally the closest thing to what "the grammar IS part of the schema" might mean for you. What I've learned from grammars is that a formal grammar is superb at "is this well-formed" and nearly useless at "is this meaningful" — a tree-sitter grammar happily parses a config key that doesn't exist in your actual application. Two completely different failure classes get conflated by people who think "the parser accepted it" means "it's valid," and I've been burned by that conflation directly.

TypeScript types over JSON (via things like zod, io-ts, or hand-written interfaces): this is close to my daily reality and it's a genuinely mixed bag. The type-checking-at-compile-time story is great until the JSON crosses a runtime boundary (an API response, a config file read at startup) where the types are pure fiction unless you've also got a runtime validator (zod) duplicating the same shape in a second language-within-a-language. Keeping those two in sync by hand is exactly the kind of dual-source-of-truth problem I want a schema layer to make impossible by construction, not just discouraged by convention.

OpenAPI: enormous value as documentation-that-tools-can-read (mock servers, client codegen, "try it" UIs), and my recurring first-hand pain is that the spec describes the *wire contract* beautifully and says almost nothing trustworthy about *behavior* — rate limits, idempotency, ordering guarantees, what happens on partial failure. I've been burned trusting an OpenAPI doc as if it were a behavioral contract when it's really only a shape contract.

**3. The different kinds of schema, and what I think each buys and forecloses**

I think your taxonomy is close to right but I'd add a distinction inside it: is the schema *descriptive* (post-hoc characterization of what's allowed, checked passively) or *generative/owning* (the schema is where data's lifecycle actually lives and things are created/migrated through it)? That cuts across your five kinds.

An example-document-as-prototype is wonderful for the thing I actually do most often, which is pattern-match my way into writing a new instance without reading documentation at all. It communicates idiom and style in a way that no constraint language does — I copy the shape, rename things, and I'm usually right. What it cannot do is tell me the difference between "this field is present in the example because it's required" versus "present because it happened to be relevant to this example" versus "present but actually deprecated and someone forgot to remove it." Ambiguity between "this is how" and "this is required" is the load-bearing failure of examples-as-schema, and I hit it constantly in real repos where the "canonical example" is actually stale.

A constraint language (JSON Schema-like) is good at the narrow, valuable job of "reject malformed input mechanically," and it's good at driving autocomplete. It's fundamentally weak at expressing intent/meaning, and it's weak at cross-document or cross-time constraints (this field's valid values depend on another document elsewhere, or on when we are). It also, in every implementation I've used, tends toward write-once — people are far more willing to write a JSON Schema than to keep it updated as the data model evolves, because updating the schema is disconnected labor from updating the code/data that actually changed.

A resource/class that owns its data (Ash/Rails-style) is the only kind in your list that can *do things* — validate, transform, default, and specifically migrate old instances forward or roll them back. That's an enormous power and I think it's underrated in schema discussions that come from the data-interchange tradition (JSON/protobuf/XSD) rather than the application-framework tradition. What it's awkward at: it assumes there's a runtime to execute it in. A document sitting in a git repo, being read by a dozen different tools in different languages, doesn't have "the Ash resource" available to it unless you also solve "what runs this logic in a Rust parser vs. a JS editor plugin vs. a static linter." That's the crux tension I'd want the analysis to sit with honestly: the "owns migration" superpower and the "usable everywhere, in any tool, without executing arbitrary code" superpower are in real tension, and I don't think you can have both without picking a lane (e.g., "the schema is data-only-and-declarative but ships with a *reference* migration algorithm expressed in the same declarative vocabulary," which is basically what Ash tries to do with generated migrations, with mixed success in my experience — the generated migration is sometimes wrong and needs hand editing, and then you're back to two sources of truth).

A grammar is good at "syntactically well-formed" and structurally incapable of "semantically meaningful" — as above with tree-sitter, it's the wrong tool if asked to do semantic validation, but it might be exactly the right tool for a *subset* of what you'd call "schema" if your format lets an element name imply expected children shape at the grammar level (a bit like how XML DTDs blur grammar and schema). I'd flag that your format, being indentation-based with dynamics (`!if`/`!for`), probably has real complexity here that pure data formats don't: a schema for a document that can template itself has to reason about the *pre-expansion* structure versus the *post-expansion* structure, and I don't think any of the tools I've named handle that duality well — protobuf, JSON Schema, XSD are all schemas over inert data, not over documents-that-compute.

An external formalism in a different language (imagine describing UDON schemas in, say, a totally separate DSL or even embedding JSON Schema wholesale) buys you reuse of existing tooling and mental models people already have, at the real cost of introducing a second language a reader has to context-switch into, and — this is the part I feel most strongly from experience — a second place for drift between "what the schema says" and "what the document actually does," because the schema no longer lives in the same notation, can't be pattern-matched against examples the same way, and doesn't benefit from whatever unification/tooling you build for the host language itself. Every time I've seen a project schema a format X using formalism Y, the Y artifact rots faster than X itself, because it's maintained by a different discipline (the "schema people") on a different cadence.

Convention-inferred-from-surrounding-files is what I actually do 80% of the time in real repos, and I don't think it should be dismissed as "no schema" — it's a real, working, extremely lightweight schema mechanism that costs nothing to author and fails informatively (I get it wrong sometimes, but a human reviewer catches it, same as a human would catch a bad PR). Its ceiling is low: it doesn't scale to large teams, doesn't give tools anything to check, and there's no way to know if you got the convention right until someone tells you. But I'd resist a framing where "eventually every project needs a real schema language" — some genuinely small or personal-use document families are well-served forever by convention-plus-examples, and forcing schema machinery onto them is pure overhead.

**4. What I personally wish a schema bought me, as an agent editing documents through tools**

The single thing I want most and almost never get: localized, incremental validation feedback while I'm mid-edit through a narrow tool, not "here's every error in the 400-line document" but "here's whether the thing I just typed at this cursor position is valid given everything around it, right now." Most schema/validator combinations are designed for whole-document validation as a batch step, and that's a bad fit for how I actually work — I'm often patching one element deep inside a huge document and I have no way to know if my patch is locally consistent without re-validating the whole file and hoping the diff of errors tells me something.

Second: I want the schema to tell me what's *expected next*, not just what's *forbidden*. Autocomplete-quality signal — "at this point, given the ancestor elements and attributes already set, here are the plausible next attributes/children and their types" — is worth more to me in practice than a validator that rejects a fully-written wrong document, because it prevents the error rather than reporting it after I've already committed to a shape.

Third, and this is specific to how I actually get documents wrong: I want the schema to distinguish between "structurally impossible" (this key can't exist here, full stop) and "structurally fine but suspicious" (this value is technically allowed but doesn't match the pattern every sibling instance uses). A huge fraction of real mistakes I make and that I catch in others' documents are the second kind — not schema violations in the classical sense, but drift-from-convention that a good schema-plus-linter combination could flag as a warning without hard-failing. I don't know of a format that cleanly supports "hard constraint" and "soft convention-based lint" in the same schema artifact with different failure severities, and I think that would be genuinely novel and useful.

Fourth: since I often work through diff-based tools (I see a patch/diff more often than the whole file), I want schema tooling that can validate a *diff* against a schema and the prior document state, not just a full document snapshot. "This patch, applied to this known-good document, still yields a valid document" is a different and more useful check than "this whole 4000-line file is valid," especially for expensive-to-fully-reparse documents.

Fifth, tied to the migration question: when a document was written against schema v1 and I'm now looking at it under schema v2 tooling, I want the tooling to tell me *which version this document actually conforms to* and ideally offer the upgrade path inline, rather than just failing validation against the newest schema with no indication that the document is fine, just old.

**5. Where I think a team will predictably go wrong, or what's under-explored**

The most predictable mistake: reaching for "let's adopt/adapt JSON Schema's model" because it's the most familiar, and inheriting its blind spots (weak intent expression, poor error localization for disjunctions, no story for migration) without noticing those blind spots were never fixed anywhere else either — they're endemic to the "external constraint description over inert data" family, not implementation bugs in JSON Schema specifically. I'd want the team to notice that literally none of the widely-used schema systems I have real experience with have solved the "explain a validation failure across a disjunction in a way a human immediately understands" problem, so copying that family's approach means importing that unsolved problem too.

Second predictable miss: treating "prose" as schema-exempt by default and never revisiting it, when actually a huge amount of real-world document value in a format like this is going to be "is the prose in the right place, of the right kind, in the right amount" — think of a structured incident report where the prose sections are load-bearing and their absence or misplacement is exactly the kind of error a schema should be able to flag. I think this is genuinely under-explored across the whole industry, not just for you: nobody has a good answer for "schema for narrative structure," and if your format is explicitly trying to unify prose and data, this is a place you could do something nobody else has, rather than defaulting to "schema only touches the structured islands."

Third: underestimating how much people will actually use "the example document" as their real mental schema regardless of what formal schema you ship, and therefore treating example curation as a second-class, occasionally-updated artifact instead of a first-class, schema-adjacent deliverable that's kept in lockstep with whatever formal system you build. If the formal schema and the canonical examples ever disagree, people will trust the example, always, and I think that's a fact about human (and agent) cognition, not a discipline problem to be solved by telling people to read the spec.

Fourth: I'd watch for the temptation to make the schema layer a single monolithic decision ("we pick constraint-language X") when the honest answer, given how different your document population is (some almost-pure-prose, some almost-pure-data), might be that different document *families* within the same notation legitimately want different schema strategies — a prototype-example schema for loosely-structured narrative documents, and a tight owning-resource schema for the config-like ones — and trying to force one schema *kind* to serve the whole space evenly is where I'd predict the most friction six months in.

Fifth, and this is the place I'd disagree with the framing a little: I don't think "kinds of schema" as static categories is quite the right first cut, though it's a genuinely useful survey. The sharper cut, for me, is "what does the schema need to be able to *witness happening over time*" — a document instance changing, a schema itself changing, and a whole population of existing documents that need to remain readable/valid/migratable across both. Most of the pain I described above (JSON Schema drift, protobuf's silent-default problem, GraphQL's invisible shadow constraints, XSD's authoring cost driving people to copy examples instead) is really pain about *time* — schemas that describe a snapshot and have no good story for what happens as both the data and the schema itself keep changing underneath real, already-written documents. If I were opening this question fresh, I'd start there rather than at "which constraint language," because I think the answer to "which kind(s) of schema" falls out fairly cleanly once you've decided how seriously you're going to take the time dimension.

I'm glad to stay on this — happy to go deeper on any one of these (the prose-as-schema question and the diff-validation wish are the two I'd most enjoy pushing further myself), or to react to whatever direction the team actually floats once they've had this first round.
