# Audit of the 0.10.1-draft suite — 2026-09-01

**Register: review findings, single reader (Fable, one session), unratified.** Method: whole first-hand reads of every file in `spec-0.10.01/` (incl. the spelling grid), the redux + matrix + def-reference + def-generator frame, the whole 0.10.0 suite (CORE, MODEL, GLOSSARY, SEMANTICS, DELTAS, CARVEOUTS, working notes), DECISIONS/OPEN, and the archived second-pass FIXTURES conventions. Then fixtures were written against the draft's text (`../fixtures/`); every case cites the section it derives from, and every case where the text would not settle the expectation went to `descriptive/` with a `gap:` id that points back here.

The draft's own review rule (README pt. 4) is applied: *a behavior differing from 0.10.0 without a DELTAS row is a defect; say so rather than pick a side.* I have not picked sides anywhere below — each item is a three-way picture (what the text says, what else it says, what a fixture author cannot decide), with a lean marked as a lean when I have one.

Ordering: the findings that would cost most if wrong first.

---

## A. Structural findings (the frame vs its own spellings)

### A1. The geometric capture is unreachable as an assignment value — a regression vs 0.10.0

§3's `<` guard: *"at a value-expected position, or at Structure Position when followed by `ident:` (block capture)."* §2.1: a value-expected position along the Line Scan **is** a Structure Position. So at `:code <python:` both clauses match, and the text gives no precedence. §6.4 says `<` is *self-announcing* at a value-expected position → the value form. §6.5 says a deferred body's first line *carries the value-expected position* → `:code` ⏎ `<python:` also reads as the value form.

Consequence: in every position where an assignment's value is expected, `<kind:` opens the **value** capture — depth-counted, delimited, spans lines until a `>` — and the geometric block form can only ever be an element **child**. 0.10.0's `|el :script !:sh: make build` (§6.8, §10.1 — "all of this holds uniformly in node-value position") has no 0.10.1 spelling: with `!:kind:` retired (DELTAS 14) and the `!` guard no longer admitting `:` (§3), a typed geometric body as an assignment value is gone. §6.3's own table promises "block capture / fence as node values" — the fence still works (its opener is not `<`); the block capture does not.

Compounding hazard: a code body that must now go through `<py: …>` closes at the first `>` in the code (`if a > b:`), and `<` `>` inside the body are depth-counted — the body of a comparison-heavy program is un-writable except via fence. 0.10.0 had the same envelope behavior but did not route code through it.

This is strain 3 seen fully: it is not a two-token *guard* wrinkle, it is a **form collision** — `<kind:` prefixes both a value capture and a block capture, and the draft's positional split does not separate them where it matters. Fixtures: `gap_A1_*` (descriptive), plus the comprehensive `cap_block_child_*` cases that show the child position working.

Options I can see (not a recommendation): (a) value-expected position wins, block form is child-only — then say so in §9.3 and admit the regression with a DELTAS row; (b) `<ident:` **followed by EOL or a space-then-tail** at *any* Structure Position is the block form, `<ident:body>` with an on-line `>` the value form — needs a bounded-lookahead argument (§2.1) since the discriminator is "is there a `>` on this line"; (c) keep `!:kind:` as the geometric spelling (CARVEOUTS §CAP's *current* text actually says this — see B2).

### A2. DELTAS 12 gives lists the span law but not the fail-safe reason — and the accident it contains is identical

§10.5/§11.2: identity brackets keep the EOL fail-safe *"because an editing accident (`|el[k`) must not swallow the document."* Lists now span ⟨P⟩ with **no** fail-safe. A forgotten `]` in `:tags [a b` ⏎ now swallows every following line into the list until EOF (→ `incomplete-input`) or the next stray `]` anywhere below. The admission rule in §11.2 — *"only with a stated accident-containment reason"* — is satisfied by lists exactly as well as by identity; the draft does not say why lists differ. Nor does it say what a **block-form marker inside a spanning list** does (`[1` ⏎ `|other :a 1` ⏎ `]`): §10.4 says items take the full value grammar, §9.2 says block forms go "nowhere [an element] can't (list items, brackets)", and neither says what the recognizer does with `|other` there — text item? terminator? warning?

README pt. 2 asks for pushback on exactly this row. Mine: the theory ("delimited means delimited") is sound as a *default*, but the fail-safe category the draft itself created is under-applied. Either lists get the fail-safe with the same reason, or the row states why the accident cost is acceptable for lists (my guess at the honest reason: multi-line lists are a real demand the identity bracket never had — but say it). Fixtures: `list_spans_lines` (comprehensive, ⟨P⟩), `gap_A2_*` (descriptive).

### A3. Trait-continue `?` vs cardinality `?` — collides in the draft's own example

§5.3: trait-continue includes `? ! * +` (`.foo?` is trait `foo?`). §9.1 ⟨P⟩: a trailing `? * +` on a reference head is cardinality. The selector subset is `name? [key] .trait*`. So `@user.admin?` is **either** name `user`, trait `admin?`, cardinality `{1,1}` **or** trait `admin`, cardinality `{0,1}` — and the text decides nothing. The draft's §9.2 exemplar is `!if @{user.admin?}`, which reads as Liquid-style "is admin" — i.e. the trait reading — while `@other[key]?` in Appendix A wants the cardinality reading. The NUANCE-AUDIT row ("the two uses reinforce rather than collide") checked the *element-suffix* collision, not this one. Fixtures: `gap_A3_*`.

Related (same family): in the bare selector, `.name` is a **trait**; in `@{user.name}` (Appendix A) and `@{post.title}` (§9.2) the draft reads `.name` as an attribute path — the addressing theory's future grammar riding in the "raw balanced head". So `@post.title` ≠ `@{post.title}` today, and nothing says so. Fixture: `gap_A3_dot_path_vs_trait`.

### A4. `$main` value vs sameline child — `|a |b` is two things at once

§2.2: `|a |b |c` "is, for all hierarchy purposes, the vertical form" — children. §6.4: block-form `|name`/`!name` at a value-expected position is a *self-announcing value*; §6.5 rule 2: on an element-rooted line further values stack as `$main`; §6.10: "self-announcing values become `$main` values." So `|a |b` is a child by §2.2 and `$main = b` by §6.4/6.5/6.10. Carried defect (0.10.0 has the same three sentences), but the draft claims full statement. The spelling grid's Element row takes the child reading; SEMANTICS 5 makes `:x |em hi` ≡ `:x |{em hi}` — which, if the `$main` reading held, would make `|el |em hi` ≡ `|el |{em hi}` too (child vs `$main` inline element). One sentence settles it: *block-form nodes at the `$main` slot are sameline children, not `$main` values.* Fixtures: `gap_A4_*`.

The same sentence cluster carries a wording defect: §6.4 "block-form `|name`/`!name` → node — self-terminate; the scan continues after each" contradicts §6.8's one-way door (the scan continues *inside* the node). Carried from 0.10.0 verbatim.

### A5. Where the cardinality suffix lives on the delimited forms is unstated

§9.1: cardinality is "trailing on the head"; the delimited forms carry "a raw balanced head **carried whole**." So for `@{posts*}` (the draft's own `!for` example) — does recognition peel `*` off and record `{0,N}`, or is `posts*` handed whole to the addressing theory? Both readings are consistent with the text; MODEL's `Reference = { head, cardinality, partial }` wants the peel. And for `@<head>`: `@<tags>*` or `@<tags*>`? Nothing. Fixtures: `gap_A5_*`.

### A6. Annotations at a value slot — DELTAS 11's Error, and the continuation collision

DELTAS 11: a slot with only annotation material has no value → the ordinary missing-value rule → **Error + Nil**. So `|el :todo ;{fill in}` and `|el :todo ; fill in` are both the sole core Error. Defensible (the value *is* absent), but note it makes the trailing-annotation idiom on a bare label an Error, where 0.10.0 gave `""` for `;{}` and — for the framed form — the same Error. Worth a sentence acknowledging it.

Then the continuation collision (carried from 0.10.0, now sharper because the draft principled opacity): §8 says a *line annotation* "owns everything indented deeper" and lists "after a finished value (framed ` ; `)" as also a *line annotation*. So `:desc ; the description` ⏎ deeper lines — are the deeper lines the annotation's continuation or the assignment's deferred body? Same for `|el ; note` ⏎ `  |child`. If the sameline annotation owns deeper lines, one trailing `;` silently swallows an element's whole body. Fixtures: `gap_A6_*`.

## B. Internal inconsistencies in the suite (checkable, no judgment needed)

- **B1. DELTAS 4 vs DELTAS 12.** Row 4: "lists/identity brackets keep current behavior *as stated rule* pending capture-sugar (CARVEOUTS §CAP)." Row 12: "**lists now span lines**." Same file, opposite claims. Row 4 predates row 12 (commit adcb185 added 11–14).
- **B2. CARVEOUTS §CAP is stale against DELTAS 12/14.** §CAP: "until then lists/identity brackets keep stated current behavior" (contradicts 12) and "the geometric capture's spelling (`!:kind:` retained-but-re-owned; a `<kind:`-headed geometric form is the alternative)" (DELTAS 14/CORE §9.3 inverted that: `<kind:` primary, `!:kind:` the alternative).
- **B3. Four geometries vs three.** CORE §9.3 + DELTAS 14: three geometries, in-flow dropped. MODEL §2 `Capture = { geometry: value|block|fence|inflow …}`, MODEL §4 `Segment = … | Capture`, GLOSSARY "Capture — … in four geometries (value, block, fence, in-flow)", README "(Generator as element-shape; Capture; …)". If in-flow is dropped, `Capture` is not a `Segment` and the enum has three members.
- **B4. §3 `!` guard vs §9.3 alias.** Guard: "followed by an identifier char or `{`" — no `:`. §9.3/DELTAS 14: "the conservative alternative retains `!:kind:` as an alias during migration." Under §3 as written, `!:sh:` fails the guard and is text; the alias is not available. Decide in one place.
- **B5. G1 vs §11.2.** G1: "Delimited constructs close by their printed closer, never by geometry." §11.2: fail-safes are early closes by geometry (EOL). "Orientation, not law" softens it, but the guiding model should carry the one exception it introduced.
- **B6. §3 `<` guard has two matching clauses at a value-expected position** followed by `ident:` (→ A1).
- **B7. Appendix A annotates inside a held body.** `print("| not udon here")     ; held span — never parsed` — under G6/§9.3 that `; …` is capture body bytes, not an annotation. The surface map contradicts the rule it illustrates (carried from 0.10.0's Appendix A, where the same line sat inside `!:python:`). Cheap fix: move the gloss to a line at the capture's column.
- **B8. §6.4's brace list omits `@<…>`** ("`|{…}`, `!{…}`, `@{…}` self-delimit") — harmless since `@` self-announces, but the held form is the draft's ⟨P⟩ bet and should appear where the others do.
- **B9. DELTAS 12's "Now" column names only lists**, but the row also newly declares strings, `;{…}`, `!{…}` and `@{…}`/`@<…>` heads as spanning (§10.5 table) — all "deliberately unspecified" in 0.10.0 §13.2. The row should list what it flips.

## C. Behavior differing from 0.10.0 with no DELTAS row (by the draft's own rule, defects)

- **C1. R13's nameless `!{` at EOF is text `"!{"`** — present in 0.10.0 §9, absent from the draft; and with `{` now in the `!` block guard the line-initial case is newly live (→ D5).
- **C2. `!` guard drops `:`** — a behavior change (§3) not rowed (DELTAS 14 speaks of the *form*, and says the alias is *optionally* retained).
- **C3. Q8 promoted to law.** 0.10.0 §6.4 marked "attached `\X` under an open value joins it" as *(Open lean — working-notes Q8)*. The draft states it flatly (§6.4). Either row it or keep the lean marker.
- **C4. Fence closer detail dropped**: 0.10.0 §10.3 "the closer must be followed by its line end" (so ```` ```rust ```` on a line is not a closer). Draft §9.3: "closes at a line whose first non-space content is ``` " — silently widens the closer.
- **C5. `\` before an inline opener in flow** (0.10.0 §7.3 "`\` before an opener makes it literal") is gone from CORE; it survives only in the working-note grid (note 7) and as `\@` in §9.1. §7.1 should carry it.
- **C6. Line-initial `|{` opening an inline element "as the first segment of a flow line, participating in hierarchy at its column"** (0.10.0 §2.2/§3) — dropped. Now also needed for line-initial `@{`, `!{`, and — note — `;{`, which by §8's table is a *line annotation* at a structural column, so `;{note} then prose` at line start swallows the whole line (and deeper lines). Fixture: `gap_D5_line_initial_semicolon_brace`.
- **C7. Carve-outs neither restated nor listed as carried/dissolved**: ENV-ROUTE, ENV-EMPTY, PATHS (→PATH, fine), PRAGMA (→VOCAB, fine), DIALECT-DEF (→VOCAB, fine), MIXIN, ANNOT, RC-SPELL. CARVEOUTS' carried list names only UNI, S4-SCOPE, S9, IND, MD, CODES, W. ANNOT is the awkward one: the word *annotation* now means `;`, and 0.10.0 §12.5's named-element annotation convention (`|{note :confidence 0.7}`) has no home or name.

## D. Gaps a fixture author cannot fill from the text (each is a `descriptive/` case)

- **D1.** `<http://x>` — kind `http`, body `//x`? The value form's kind charset is unstated (block form says `ident:`); `<2026-01-01T10:00:00>` is safe only if kind must be an identifier. Is the one-space-after-`:` separator rule of 0.10.0's inline verbatim (§10.2) now family-wide (`<u64: 5>` body `5` or ` 5`)?
- **D2.** Block-form ladder: `<temporal:interval:` at Structure Position — vocab+kind, or kind `temporal` with tail `interval:`?
- **D3.** `<python:foo>` on its own line at Structure Position (no value expected): block form with tail `foo>`, or value form as a… what node?
- **D4.** Nested spanning form inside a fail-safe bracket: `|el["abc` ⏎ — the string spans, the bracket does not. Innermost-first says the string is still open; the fail-safe says the bracket closes at EOL. Which wins?
- **D5.** Nameless inline generators: is `!{}` valid like `|{}`? The breaking note says `!{{expr}}` "is an inline generator named nothing" (body `{expr}`) — so yes? And `!{` at EOF (R13)?
- **D6.** Bare `@x` inside `[…]` — §6.4 says the full value grammar applies in list items *and* identity brackets, with `@` self-announcing; §5.3 says references in identity take `@{…}` and bare `@` is out of the sugar. What does `|el[@x]` produce — text `"@x"`? a reference? And in a list, `[@x]` is presumably a reference item (§10.4 lists references) — so the two brackets differ, contra K16's "no divergence between key interiors and normal values"?
- **D7.** Block forms inside brackets/lists: `[|x]`, `[!if x]`, `[:a 1]` — "out of the sugar" says nothing about the keep shape.
- **D8.** Identity bracket unclosed **at EOF**: EOF ≡ EOL fires the fail-safe → `complete`, or §11.3's "delimited still open at EOF → incomplete-input"? 0.10.0's vignette 2 leaned complete.
- **D9.** A block `@head` line followed by deeper lines — references are in neither the geometric nor the delimited list (§11.1). Do deeper lines belong to it?
- **D10.** Framed `\` inside `|{…}`: it "holds the rest of the physical line, dead to markers" — including the `}`? DELTAS 13's example `|{a :title Home \ Welcome! ; hm}` assumes `}` still closes.
- **D11.** `|el?foo` — suffix then junk; `@x!` — `!` is not a cardinality; `!1` — "identifier char" (start or continue?).
- **D12.** Floats with `_` (`1_000.5`); `.5`; `1.`; `1e5` vs `1E5`; `0x` alone; `1__0`.
- **D13.** Adjacent strings in a slot: `:x "a""b"` (lists rule it two items; slots say nothing).
- **D14.** `;{…` spanning lines in prose (now declared spanning ⟨P⟩) — one unclosed inline annotation holds the rest of the document as annotation body; is that intended?
- **D15.** ROOT-BASE and SEMI-BASE from OPEN.md are still open and the draft still doesn't state the root content base or disambiguate "in block text at the content base" (line-start `;` vs mid-line framed ` ; `).
- **D16.** `@<a<b>>` / `@{a{b}}` — "raw balanced head": balanced in which delimiter, and depth-counted like captures?
- **D17.** `:a ;{x} 5` — annotation then a value in the same slot: does `5` fill the slot (no Error)?

## E. Things that hold (checked, not just read)

The material half is as solid as the NUANCE-AUDIT says: the Nesting Rule, `$main`-as-sugar, the K10 terminator set, the hold split (attached/framed), stacking, the four states, numbers, strings, keep-everything, and EOF ≡ EOL + dedent all produced unambiguous fixtures straight from the text — 70-odd comprehensive/idiomatic cases with no judgment calls. The value-expected-position principle (K16) really is one sentence doing the work of a table. DELTAS 13's hold-precedence resolution of the `\ … ; ` edge checks out, and DELTAS 11 is the more principled reading of `;{}` even though it is the harsher one.

The one strain I would upgrade: strain 3 is structural (A1), not lexical. The one strain I would downgrade: strain 1 (framed ` ; ` terminating a value) is exactly what the annotation's *position table* already licenses — an annotation has to begin somewhere; it is a convention, not a fight with the frame.
