## My leans on what we raised and didn't finish

He wants these: "*your* lean and recommendations on anything/everything are very useful data-points to me even if I end up leaning another direction". Give yours too, and "this is what I would expect" is a valid reason.

- **Label characters.** Two reports are in `.int/`, read in order: `labels-unicode-options-2026-10-20.md` (from UAX #31 rev 45, UTS #55, XML 1.0, CSS Syntax 3, KDL v2; Unicode facts checked against UCD 18) and `labels-ascii-and-positions-2026-10-20.md`. My leans:
  - XML's fixed ranges for non-ASCII, with "does `|` open an element?" separated from "is this a valid name?", an invalid name being an error rather than text;
  - one character set for every label;
  - `-` `:` `/` `?` `*` `+` inside, `_` anywhere, `$` first only, no leading digit;
  - `!` `@` `#` `=` and the rest an error ("quote it");
  - quoted equals bare; case never folded; byte equality plus a default-off NFC warning;
  - no controls, bidi controls or noncharacters in any label, even quoted.

  He hasn't answered part 1 yet.
- **The value model.**
  - Bare `hello` and `"hello"` are both strings, differing only in form (`bare` / `double`, kept in «meta»).
  - A «text» is only for mixed content (runs plus embeds plus `;{…}`).
  - Two axes: **kind** (what the value is, hierarchical: `number.int`) and **form** (how it was written). One dotted suffix for both would make `x.y` ambiguous.
  - A stack of occurrences and a list value read the same to a consumer, with `stacked` vs `bracket` kept as form.
  - Whether a lone embed *is* the value is still open.
- **Comments among an attribute's items.** I pushed back with "a comment isn't a value" and he caught it: it was an objection to his drawing, not semantics. Withdrawn. In the three-layer picture (tree / views / meta), comments are items wherever they sit, and "skip comments" is a view.
- **`<…>` with primitives inside.** Yes; it's what I'd expect `<…>` to mean. The edges: the interior must match wholly (`<1.2.3>` is raw); `< 3 >` trimmed?; in `<"a>b">` the string is read first; lists not included. The name: «primitive value», since "typed" is redundant when every value has a type.
- **Tree notation.** `⸨…⸩` for a «text», `⟬…⟭` for raw, `"…"` for strings, `[…]` only for a UDON list value. AST sequences never take brackets. `<…>` never appears in a tree. Backticks stay for the fence node, since tree fragments are quoted inside backtick code spans in prose. Don't reuse «…» for literal characters.
- **«string» as a term.** After the pass, what's left is the value kind a delimited string gives. If bare words are strings too (the value model above), «string» is the kind and «delimited-string» the spelling; that's the direction I'd take it.
- **Grammar.** PEG for everything inside a line (its ordered choice matches the guards), with Python-style NEWLINE/INDENT/DEDENT from a short prose line layer. Start with productions in `def-delimited-string` and `def-characters`, since those are settled or nearly. Writing productions exposes undecided edges, which is useful in itself (the key `|x["a]b"]` case fell out of the key card this way).
- **`~~~` fences.** His lean is to accept both ```` ``` ```` and `~~~`. A ```` ``` ```` fence also protects Markdown code blocks written in UDON prose, which is why `~~~` can't replace it.

## Working with Joseph: what helps

Most of this is also in the project memory; it's here so you meet it whole.

- **Bring one small thing at a time**, as UDON examples plus counter-examples, with other syntax mixed in, and the tree each lean would give. Never a coined ID or a pre-design number.
- **Say how settled you think it is**: "This is right, right?" when the cards support it; "I'm not sure X is settled" when they don't. Don't assert an inference as a derivation, and don't assume something undiscussed is a rule (embeds, `$main` in braces, whether fences are elements).
- **Record his words verbatim every turn** in `.int/STEWARD-VERBATIM.md`: his whole message, your side summarized. Then edit the affected cards in the same turn and commit with pathspec `v2/spec-lite-0.1.0`. Never push.
- **When he ideates, write it down and engage**: push back, remind, counter, with your instincts. Push back on the semantics, not on his ad-hoc notation. He told me that directly when I argued with how he drew a tree.
- **Never present an agent's summary as his words.** I called something "the same kind of retroactive shape change you objected to for `$main`" on the strength of an agent's summary line in the verbatim record. When I finally looked at the primary, it showed him on 2026-08-09 holding that stacking turns a scalar into a list, and rebutting an agent's "retroactive" argument as "plausible-sounding nonsense". Check the primary before you invoke what he said.
- **Leans versus rulings**: leans are cheap to revisit, rulings propagate. Record his own word, and pick `strength` from it ("lean" → `lean`; "right" / "go ahead" / "agree" → `decided`; "for right now" → `provisional`).
- **The vocabulary is as important as the rules.** I listed it as one open item among many in my first status and he called that out. It's first now.
- **He does think in long arcs and types tersely.** If an ask is thin, ask him where it's going before building on a guess.

## Meta-learnings from today
