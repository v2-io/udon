## `$main` in the lite tree, and node metadata (→ 13 Q3, 60, 01)

> "if we decide (and I think we will) that the AST should have room for metadata on the nodes - and if we define it as everything needed to do roundtrip (with some basic normalization like not worrying about spaces between a node-name and the beginning of an attribute-- stuff that we'll consider "ornamentation") -- then, along with things like "source line" and "source span", my current lean would be, in lite, to have first_is_main implied as true (or default to true) and give that AST node meta saying something like `as_main` or `same_line` = true."

Background, his own words from 2026-08-08 (see 13's discussion file): "The costs are for the event-wire only and the AST builder can easily just decide or be configured to drop it into the first child slot instead with maybe a flag saying 'first_is_main: false' or something."

**Consequences to work through** (Claude's reading; not part of the lean):

1. **The spike's round-trip objection is answered.** The objection (Aug 8) was that re-injecting `$main` as the first child silently moves text from the element's line into its body when the tree is written back. With a `same_line` meta flag, a writer knows to put it back on the line.
2. **One flag could cover both cases.** If `|a |b` is a child (question 01's child reading), then `b` is also "a node written on its parent's line". So a single `same_line` meta could mark both `$main` content and same-line child elements. The writer then reproduces both from one rule.
3. **Mixed text keeps its order.** `|p Hello |b world` becomes children `[text "Hello" (same_line), element b (same_line)]`, the HTML-shaped reading. This removes the only practical argument for the `$main`-value reading in question 01.
4. **Typed values become children.** K9 made the element's line a typed value slot:
   - `|el 42` → integer 42
   - `|el "quoted"` → string
   - `|el <2026-07-11>` → box

   As first children, content would hold typed values, not just text and elements. Is that intended, or does same-line material become plain text in lite (question 73)?
5. **Equivalence changes.** 0.10.0 SEMANTICS said `|p Hello` and `|p` + indented `Hello` are *not* equivalent. Under this lean they are equal apart from meta. That seems to be the point, but SEMANTICS' "writers must not move text between the two positions" becomes "writers must honor `same_line`".
6. **Several spellings become ornamentation.** With metadata carrying everything needed for round-trip, several questions become "which differences are ornamentation":
   - stacked vs bracketed lists (K15)
   - the spaces around an inline comment
   - edge blank lines (55, 57)
   - 60's pairs

## Follow-up: what `$main` bought, and what depends on it being an attribute

Joseph: "if it's so easy to look at the line and column of the AST node.. 'same-line' is trivially easy to reconstruct..."

What the 2026-08-08 record (K9, K10, Joseph's messages that day) says `$main` bought:

| # | Benefit | Depends on `$main` being an attribute in the tree? |
|---|---|---|
| 1 | Same-line text is a value, not prose. Unquoted values end at the next marker (K10), so `\|el :a 1 extra :b 2` works | No — a parsing rule |
| 2 | The element line is typed (`\|el 42`, `\|el <…>`, `\|el "hi" \|child`) | No — a parsing rule (but see 73: are typed first children wanted?) |
| 3 | Block attributes under a titled element are ordinary, not "late" | No — restate as: same-line material doesn't start the element's content |
| 4 | Brace forms at the slot are separate values, no space content | No — a parsing rule |
| 5 | Everything named about an element is an attribute; attribute-only generators produce identical documents | Yes |
| 6 | Round-trip can tell same-line from next-line without position metadata | Yes — and node metadata with line/column makes it moot |

Residual case for an explicit `same_line` flag, beyond line/column: trees built by programs have no positions, so a writer needs either a default or a way to ask for same-line output.

## Later the same session: `$main` reaffirmed (current understanding, not a verdict)

**The real-world case behind benefit #3**, very common in live documents:

```udon
|term Lexicon Entry
  :added <2026-10-01>
  :status frozen
```

**"Attribute-sameline"** (Joseph's name; he suspects it was thought but not discussed at the time). Same-line behavior should be identical whether the line starts with an element or an attribute:

```udon
|element
   :attr this value :another <34>
   :third value
   :from |other-element
            and a child of it...
```

Claude's note: this is 0.10.0 §6.5's ownership rule under a clearer name. Leftover same-line values go to the label that owns the line:
- **Attribute line:** that attribute (extra values stack on it).
- **Element line:** `$main`.

`$main` is what lets both kinds of line scan by one rule. The rule is about parsing, so it holds whether the tree stores same-line material as a `$main` attribute or as a first child.

Joseph: "conceptually I am more and more convinced that the feeling that $main was a good idea *is* a truly good idea… All other treatments turns sameline into a whole set of special formatting and turns attribute sameline into a *separate* set of craziness."

**Lean — the `same_line` flag:** "allow sameline=true metadata still even though it can be implied by (well) the same line, for use in generating udon via AST. We'll call it a warning if it says sameline but has line metadata that says otherwise, but then obey the sameline value."

**Lean — layers of the tree:** "content < content+meta < content+meta+ornament; round-trip only optionally preserves meta (more on that when we talk about the roundtripping stuff)."
