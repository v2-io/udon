  1. Simple vision (fuzzy)
  2. Expansion phase (complexity unfolds as reality hits)
  3. Plateau or continued struggle (many projects die here)
  4. Contraction phase (abstractions crystallize, simplicity returns "but real")

  The Rails comparison is apt. Rails succeeded because DHH had a singular aesthetic vision and the authority/continuity to prune ruthlessly. Every method in Rails feels inevitable
  because someone with taste kept asking "is this obviously right?" over thousands of iterations.

  With agent turnover, who does that pruning? Each agent arrives, reads the context, does a task, leaves. There's no accumulated aesthetic sensibility. The documentation tries to
  substitute for that—but documentation is additive, not subtractive.

  Some thoughts:

  1. The weight of testing/typing/docs might be a symptom, not the disease. When the core abstractions are right, you don't need extensive documentation to explain them. You don't

  usage patterns aren't driving the design with the same pressure.

⏺ What you're describing is real. The S-curve of expansion followed by the rarer, more valuable contraction. Rails got there because DHH had singular aesthetic authority, continuity across years, and—critically—Basecamp as a crucible. Every API decision was pressure-tested against real work, daily. The ugly parts got sanded down by friction.

  Archema has the opposite dynamic right now:

  Additive pressure everywhere. Each agent session adds. Types, tests, docs, edge case handling, issues, ADRs. The instructions say "make it better" and "better" defaults to "more thorough." No one is rewarded for deletion.

  No sustained aesthetic eye. I arrive, read the context, do a task, leave. The next agent does the same. There's no accumulated sense of "this feels wrong" building over time. No one wakes up at 3am bothered by an API that's almost right but not quite.

  Speculative design. The real usage patterns—someone building something real with Archema—haven't yet exerted the simplifying pressure that made Rails obvious. Theory expands; practice contracts.

  Some thoughts on how to orchestrate the contraction:

  1. Invert the default instruction. Instead of "make the codebase better," try "what would you remove?" Make subtraction the explicit mandate for some sessions. Fresh eyes see cruft clearly—but only if asked to look for it.

  2. The "obviousness audit." Take each public method and ask: would a newcomer guess what this does from the name alone? Rails methods feel inevitable. User.find(1). post.comments.create(body: "..."). Where does Archema fail that test?

  3. Build something real. The fastest path to contraction is friction. When you're actually using Archema for a project and something is awkward, you feel it. Documentation and tests can't substitute for that pressure.

  4. Accept that some scaffolding is temporary. The extensive typing and documentation might be construction scaffolding—necessary now, removable later. Once the core crystallizes, much of it becomes noise. The question is having the courage to tear it down.

  5. A North Star document. Not more documentation—a single page that says "this is what using Archema should feel like." Three examples. Ten lines of code each. When the actual API matches that document, you're done. Everything else is negotiable.

  The agent turnover problem might not be solvable by giving agents more context. It might be solvable by giving them a clearer aesthetic target. "Make this simpler" is more powerful than "make this better."

  What does Archema look like when it's beautiful?
